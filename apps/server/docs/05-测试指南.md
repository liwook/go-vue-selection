# 05 - 测试指南

本项目有两层测试，通过 Go build tag 严格隔离。本文说明它们的区别、怎么跑、覆盖什么，以及怎么新增用例。读完就不会再「很懵」了。

---

## 一、两层测试的区别

| 维度 | 单元测试（Unit） | 集成测试（Integration） |
| --- | --- | --- |
| 测什么 | 单个函数 / 方法 | 整条 HTTP 接口链路 |
| 是否连数据库 | **否**（纯内存、mock） | **是**（需运行中的服务 + PostgreSQL） |
| 是否需要起服务 | 否 | 是 |
| 运行命令 | `go test ./...`（默认即跑） | `go test -tags=integration ./tests/...` |
| 速度 | 毫秒级 | 慢（依赖环境） |
| 失败原因 | 明确是该函数逻辑错 | 可能是网络 / 数据 / 服务任意一环 |
| 隔离方式 | 无（或被测函数本身无外部依赖） | 文件带 `//go:build integration` 标签 |

**一句话**：单元测试验证「我的代码对不对」，集成测试验证「整个系统通不通」。两者互补，不是替代。

---

## 二、单元测试（不连数据库，日常默认跑）✅ 已落地

覆盖的是**不含 SQL / 网络 / 文件调用**的纯逻辑函数。无需任何环境，高频运行、可进 CI。

> 状态：第二章列出的 5 个包测试文件均已创建并通过 `go test ./...`，无需额外环境即可运行。

### 运行

```bash
# 方式一：直接用 go 命令（推荐，最通用）
go test ./...

# 方式二：通过 Makefile（与前端 pnpm 解耦，仅管 Go 后端）
make test          # 等价于 make test-unit
make test-unit     # go test ./...
make vet           # go vet ./...

# 只跑某个包
go test ./pkg/idconv/... ./service/...

# 看详细过程
go test -v ./pkg/...
```

### 用例清单

| 包 | 测试文件 | 覆盖内容 | 状态 |
| --- | --- | --- | --- |
| `pkg/idconv` | `idconv_test.go` | `ToStr` / `ToInt64` / `ToInt64Safe` / `ToStrPtr`（含 nil 指针降级为空串、溢出边界值） | ✅ |
| `pkg/jwt` | `jwt_test.go` | `GenToken` / `ParseToken` 往返、密钥不匹配报错、算法混淆（`alg=RS256`）防护 | ✅ |
| `pkg/snowflake` | `snowflake_test.go` | `Init` / `GenID` 唯一性、未初始化时 `GenID` 会 panic、`sync.Once` 幂等 | ✅ |
| `pkg/result` | `result_test.go` | 错误码 `Msg` 文案（含未注册码→未知错误）、`httpStatusForCode`（99 域→500）、`ErrorExternal` 对外脱敏 | ✅ |
| `service` | `convert_test.go` | `derefStr` / `derefInt64` / `pageCount` 及全部 11 个 `modelTo*` 字段映射、nil 指针降级 | ✅ |

> 测试文件与源码**同包**（如 `pkg/idconv/idconv_test.go` 也是 `package idconv`），因此可直接测未导出的函数（如 `httpStatusForCode`）。
> 断言使用标准库 `testing` 包（表驱动），未引入 `testify`，保持零额外依赖。

## 三、集成测试（需起服务 + 数据库）

`tests/` 下所有 `.go` 文件都带 `//go:build integration` 标签。**默认 `go test ./...` 不会运行它们**，避免无服务 / 无库环境下误报。只有显式带 `-tags=integration` 且服务已启动时才会执行。

### 前置条件

1. PostgreSQL 可达（连接配置见 `etc/config.yaml.example`，本地复制为 `etc/config.yaml` 后填写真实值）。
2. **无需手动起服务**：`TestMain` 会在测试进程内用 `httptest` 自动拉起真实 router，跑完自动关闭。

> 若想改为打**外部已启动**的服务（例如远程/容器环境），设置环境变量
> `API_BASE_URL=http://127.0.0.1:10086` 即可跳过内部拉起。

```bash
# （可选）如需打外部服务而非内部拉起
API_BASE_URL=http://127.0.0.1:10086 go test -tags=integration ./tests/... -v
```

### 运行

```bash
# 测试内自动拉起服务，无需先 go run main.go
go test -tags=integration ./tests/... -v

# 切换被测环境（如容器 / 远程）
API_BASE_URL=http://127.0.0.1:10086 go test -tags=integration ./tests/... -v
```

### 用例清单（按业务域拆分）

### 关键约定

- `tests/client.go`：统一 HTTP 客户端、登录取 Token、统一响应（`{code,message,data}`）解析。
- 断言以响应体 **`code` 字段**为准（本项目业务错误返回 HTTP 200、系统错误返回 500，**不能只看 HTTP 状态**）。
- 写操作测试结束自动清理新增数据；商品分类接口无删除能力，新增数据会保留（可接受的小副作用）。

## 四、怎么新增测试

### 新增单元测试

适合：纯逻辑 / 计算 / 类型转换 / 只依赖内存与标准库的函数（如 `pkg/` 下的工具，`service/convert.go` 这类转换函数）。

1. 在被测包内新建 `xxx_test.go`，`package` 与被测代码相同。
2. 用表驱动测试 + 标准库 `testing` 断言（当前未引入 `testify`，保持零依赖；如需可用 `go get github.com/stretchr/testify/require`）。
3. 若被测函数内部有真实 SQL 调用，要么用 `go-sqlmock` 桩掉 `*sql.DB`，要么放到集成测试里跑——**不要**在单元测试里连真实库。

示例骨架：

```go
package idconv

import "testing"

func TestToStr(t *testing.T) {
    if got := ToStr(123); got != "123" {
        t.Errorf("ToStr(123) = %q, want %q", got, "123")
    }
}
```

### 新增集成测试

适合：涉及 DB 读写、事务、跨表关联的端到端验证。

1. 在 `tests/` 下新建 `xxx_test.go`，**第一行必须加** `//go:build integration`（build tag 与 `package` 之间需空一行）。
2. 通过 `tests/client.go` 的 `APIClient` 发请求，复用 `TestMain` 已登录的会话。
3. 写操作后记得清理数据。

```go
//go:build integration

package tests

import "testing"

func TestMyFlow(t *testing.T) {
    // 通过 apiClient 调用接口并断言
}
```

## 五、CI / 日常建议

- **每次提交前**：`go test ./...` + `go vet ./...`（秒级、不连库，必须全绿）。
- **集成测试**：在具备服务 + PostgreSQL 的环境（如预发 / 容器）下用 `go test -tags=integration ./tests/...` 跑。
- 不要为了图省事把单元测试写成连库的集成测试，那样会拖慢反馈、引入环境噪声。
