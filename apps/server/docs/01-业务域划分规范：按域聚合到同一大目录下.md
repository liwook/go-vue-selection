# 业务域划分规范：按业务域聚合到同一大目录下

> 本文说明项目应**如何把一个业务域的所有代码聚到一个大目录下**（横向按域聚，纵向按层用单文件切）。
> 配合《分层结构体使用规范：handler、service、repository 与 types》阅读：分层讲"层内怎么传参"，本文讲"一个域的代码放哪"。

## 一、目标：一个业务域 = 一个大目录

当前项目是**按层平铺**的——`handler/`、`service/`、`repository/`、`types/` 各是一个平铺包，所有域混在一起：

```text
handler/      service/      repository/    types/
  user.go       user.go       user.go        user.go
  role.go       role.go       role.go        role.go
  menu.go       menu.go       menu.go        menu.go
  sku.go        sku.go        sku.go         sku.go
  ...           ...           ...            ...
```

按业务域聚合后，每个域是一个**大目录**，域内按层用单文件切分（每域一个 Go 包）。完整布局如下：

```text
cmd/
  server/
    main.go                # 应用入口：初始化配置、DB，注入依赖

internal/
  acl/                     # ███ 权限域（包名 acl）
    handler.go             # 接收 HTTP 请求（薄）：NewUserHandler / RegisterRoutes / RegisterPublicRoutes
                             #   → 在此定义 UserService 接口（消费方定义）
    service.go             # 业务编排（中）：NewUserService / 业务方法，持有 repo，做 model↔DTO 转换
                             #   → 在此定义 UserRepo 接口（消费方定义），userService 实现之
    repo_impl.go           # 仓储实现（Implementation）：GORM/SQL 操作，实现 service.go 里的 repo 接口，对应 dal/model
    types.go               # API 层结构体（types）：ParamXxx / ResponseXxx 等入参出参 DTO
    code.go                # 本域错误码：基于共享 ResCode 的 ACL* 段（CodeNeedLogin / CodeUserExist ...）
  product/                 # ███ 商品域（包名 product）
    handler.go             # category/trademark/attr/spu/sku/file 的路由与请求处理
                             #   → 在此定义各业务 Service 接口（消费方定义）
    service.go             # 商品业务编排（sku 经 service 持有 spu 的 repo）
                             #   → 在此定义 repo 接口（消费方定义），实现仓储契约
    repo_impl.go           # 仓储实现：实现 service.go 里的 repo 接口
    types.go               # API 层结构体（types）：ParamXxx / ResponseXxx 等入参出参 DTO
    code.go                # 本域错误码：基于共享 ResCode 的 Product* 段（CodeTrademarkErr / CodeSpuDBErr ...）
  config/                  # 应用配置（启动读取，平铺在根，由 cmd/server/main.go 直接加载）
  pkg/                     # ███ 共享内核（Common，公共库）
    middleware/            # JWT、CORS、日志等中间件（现有 middlewares/ 挪入）
    result/                # HTTP 统一返回封装（现有 pkg/result/response.go 挪入）
                             #   + 系统级错误码（SysBase 段：CodeDBError / CodeServerBusy / CodePanic ...）
                             #   + 共享类型 ResCode 与通用 Error/Success 函数
  router/
    router.go              # 路由注册 + 集中依赖装配：NewXxxHandler(...) 注入 service

dal/
  model/                   # GORM Gen 生成，按表聚合，不随域移动
    users.gen.go  role.gen.go  menu.gen.go
    category.gen.go  trademark.gen.go  attr.gen.go  spu.gen.go  sku.gen.go
  query/                   # GORM Gen 生成的动态查询构造器（按表聚合，不随域移动）
    users.gen.go  role.gen.go  menu.gen.go
    category.gen.go  trademark.gen.go  attr.gen.go  spu.gen.go  sku.gen.go
go.mod
go.sum
```

**核心区别**：改一个业务，只需打开它的大目录，域内所有层文件都在手边；不用在四个平铺包之间来回跳。

## 二、为什么用"域大目录 + 单文件平铺"（而不是子目录聚合）

| 方案 | 结构 | 问题 |
|------|------|------|
| 子目录聚合 | `acl/{handler,service,repo,types}/` 各自独立包 | 包名要加前缀（`aclhandler`）绕开冲突；域模块少时过度切分，目录层级深 |
| **域大目录单文件（推荐）** | `acl/` 下一个包，`handler.go`/`service.go`/`repo.go` 等平铺 | 符合 Go"目录=包"习惯，文件集中、跳转少；层间靠约定隔离 |

> Go 的包以目录为单位。域大目录下所有文件同属一个包（如 `acl`），层与层靠文件分工 + 约定隔离，而非靠包边界强制。这要求团队遵守第三节的纪律，否则同包内会互达私有成员。

## 三、域内分层与依赖方向

每个域大目录内部，**按文件做四层分工**，和《分层结构体使用规范》一致：

```text
handler.go   ← 只接 Gin 请求/响应（用 types.go 的 ParamXxx/ResponseXxx 绑参），调 service，自己不写业务（薄）
   │  import
   ▼
service.go   ← 业务逻辑，持有 repo 接口，做 dal/model ↔ types 转换（中）
   │  import
   ▼
repo_impl.go ← 实现 service.go 里的 repo 接口，只做 dal/model 的存取（薄），不依赖 types
   │  import
   ▼
dal/model    ← GORM Gen 表映射 PO（不随域移动，见 dal/ 段）

types.go     ← API 层结构体（types）：ParamXxx / ResponseXxx，被 handler 与 service 共用，repo 层不依赖它
```

**依赖铁律**：

- 方向单向：`handler → service → repo_impl → model/dal`，禁止反向。
- **接口由消费方定义（Go 惯用法 consumer-defined interfaces）**：`UserService` 接口写在 `handler.go`（handler 是 service 的消费方），`UserRepo` 接口写在 `service.go`（service 是 repo 的消费方）。实现方（`*userService` / `repo_impl.go`）各自满足接口即可，**不单独建 `repo.go` 放接口**。
- `repo_impl.go`（实现）在域内实现 `service.go` 里定义的 repo 接口；别的域只调本域 service，**repo 绝不跨域 import**。
- 示例：`product/service.go` 通过 `NewSkuService(skuRepo, spuRepo)` 在 service 层组合 SPU 的 repo（repo 接口也定义在 product/service.go 内），而不是 `product/repo_impl.go` 去 import 另一个 repo 实现。
- `handler.go` 必须薄：只绑参、调 service、用 `pkg/result` 封装返回，业务全在 `service.go`。

### 错误码按域划分（不集中在共享层）

错误码**跟随业务域**，不堆在全局 `code.go`。拆分原则：

- **系统级**（`SysBase`：DB/缓存故障、服务繁忙、panic 等）留 `pkg/result/code.go`，这里同时定义 `ResCode` 类型与 `Error/Success` 函数，各域复用。
- **业务级**按域下沉：ACL 的 `ACL*` 段放 `internal/acl/code.go`，Product 的 `Product*` 段放 `internal/product/code.go`，各自基于 `ResCode` Base 偏移（如 `ACLUserBase = 1000 + ...`），维护本域 message。
- **禁止跨域引用**：域 A 不得 import 域 B 的 `code.go`；确需共用就提升到 `pkg/result` 的系统级段。

> 这样改后，"一个业务域 = 一个目录"才彻底自洽：改 ACL 的错误提示，只需打开 `internal/acl/code.go`，不必翻全局大文件。

## 四、当前域清单与落点映射

| 业务域 | 路由前缀 | 当前平铺文件（handler/service/repository/types） | 聚合后大目录 |
|--------|---------|-----------------------------------------------|-------------|
| **权限域 ACL** | `/api/v1/acl` | user、role、menu（+ pkg/result 的 ACL* 段） | `internal/acl/{handler,service,repo_impl,types,code}.go` |
| **商品域 Product** | `/api/v1/product` | category、trademark、attr、spu、sku、file（+ pkg/result 的 Product* 段） | `internal/product/{handler,service,repo_impl,types,code}.go` |

> `file`（文件上传）随商品域走，作为 `product/handler.go` 内的文件处理部分，不对应独立业务表。
> 跨模块多的域（如 product 含 sku↔spu）可在 `service.go` 内部分函数组织，不强行拆文件。

## 五、跨域依赖怎么写

聚合后跨域调用写成 **import 对方域包**：

```text
product/service.go
   import  internal/acl        ❌ 商品域不应依赖权限域（实际无此需要）
product/service.go
   import  internal/product    ✅ 同域内 sku 业务持有 spu 的 repo（经 service 组合）
acl/service.go
   import  internal/acl        ✅ 同域内 user 业务持有 role 的 repo
product/repo_impl.go
   import  internal/product    ❌ repo 实现不得 import 另一域的 repo 实现
```

实际装配（参考 `router/router.go`）集中在 `internal/router` 包做依赖注入，Handler/Service/Repo 的构造参数类型换成各域包的返回值。

## 六、迁移操作清单（以商品域为例）

1. 建 `internal/product/`（单包）。
2. 合并文件：`handler/*.go`→`handler.go`、`service/*.go`→`service.go`、`repository/*.go`→`repo_impl.go`、`types/*.go`→`types.go`；接口写在消费方（handler 定义 Service、service 定义 Repo），无 `repo.go`/`domain.go`。
3. 改 `package` 为 `product`，更新 import 路径与构造函数引用。
4. `dal/{model,query}` 不动（GORM Gen 生成）。
5. 共享件归位：`middlewares/`→`pkg/middleware/`；`config/` 平铺根目录；系统级错误码与 `ResCode` 留 `pkg/result`。
6. 拆错误码：`ACL*`→`internal/acl/code.go`，`Product*`→`internal/product/code.go`，各域 `code.go` 只定义本域常量。
7. `main.go` 上移到 `cmd/server/`，`router.go` 仅更新 import 路径，保持集中装配。

> 迁移可**逐域进行**：先挪 product，再挪 acl，未迁移的域暂时还留在原平铺包，Go 允许新旧结构并存，不必一次性全改。

## 七、一句话总结

> ## 一句话总结
>
> ### 一个业务域 = 一个大目录 （单包多文件）
>
> - **域内文件**：`handler.go` / `service.go` / `repo_impl.go` / `types.go` / `code.go`
> - **接口由消费方定义**：`handler.go` 定义 `Service` 接口，`service.go` 定义 `Repo` 接口；无独立 `repo.go`、无 `domain.go`
> - **错误码按域划分**：业务级 `code.go` 在域内，系统级留 `pkg/result`
> - **共享与配置**：`config/` 平铺根目录，`pkg/`（`middleware`、`result`）作共享内核；`dal/{model,query}` 不随域移动
> - **依赖单向**：`handler → service → repo_impl → dal/model`，跨域只经 service；改业务只需打开它自己的目录
