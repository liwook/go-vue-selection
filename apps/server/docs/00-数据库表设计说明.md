# 数据库表设计说明

> **本文档是开发的起点。** 本项目的工程顺序是"先建表、后写码"：`init-sql/init.sql` 定义表结构 → GORM Gen 从表生成 `dal` 的 model/query → 再基于 model 写 repository/service/handler。因此请先读本文理解表结构，再往下看 `01~04` 的分层与规范文档。
>
> 本文档说明 `init-sql/init.sql`
> 的表设计与外键改造内容：每张表的作用、为什么建这些表、外键为什么要加、加了哪些、以及改完后对业务代码的影响。

## 0、各表作用与建表原因

本系统是一套**后台管理系统**，数据模型围绕两大主题展开：

1. **电商商品域**：类目（三级分类）、品牌、平台属性/销售属性、SPU/SKU
   及其图片、属性值关联——对应后台"商品管理"模块。
2. **权限域（RBAC）**：用户、角色、菜单，以及用户-角色、角色-菜单两张关联表——对应后台"权限/账号管理"模块，含账号锁定（`users.status`）。

下面按主题说明每张表**为什么存在**、**解决什么问题**。

### 1. 商品类目（三级分类树）

| 表 | 作用与建表原因 |
|----|----------------|
| `category1` | **一级分类**。商品类目树的最顶层（如"电子数码"）。作为整棵类目树的根，不依赖任何其他表，是所有下级类目和商品的最终归属锚点。 |
| `category2` | **二级分类**（如"手机通讯"）。必须挂在某个一级类目下才有意义，因此 `category2.category1_id` 引用 `category1`。 |
| `category3` | **三级分类**（如"智能手机"）。平台属性和 SPU/SKU 都绑定到**三级**类目（后台要求选到三级才能加属性、建商品），是商品类目树中最"细"的一层；`category3.category2_id` 引用 `category2`。 |

> 为什么拆成三张表而不是一张"带 parent_id
> 的自关联表"？因为电商场景里三级分类与属性、SPU
> 的绑定关系是**固定的三级**，拆表后每一级结构清晰、索引和外键约束更直接，也便于按层级做统计与展示。

### 2. 品牌

| 表 | 作用与建表原因 |
|----|----------------|
| `trademark` | **品牌/商标**（如"Apple""华为"）。SPU 与 SKU 都必须归属一个真实存在的品牌。品牌是商品维度的独立主数据，被 SPU/SKU 引用，删品牌会受 `RESTRICT` 保护。 |

### 3. 平台属性

| 表 | 作用与建表原因 |
|----|----------------|
| `attr` | **平台属性**（如"颜色""内存""屏幕尺寸"）。平台统一定义的规格维度，挂在三级类目下（选到三级分类才能给该类目加属性）。 |
| `attr_value` | **平台属性值**（如"颜色"下的"白色/黑色/金色"）。从属于某个 `attr`——同一个 `attr_id` 可重复出现多行，正是"一个属性有多种值"的体现。`attr` 被删时，其下属性值失去意义，故 `CASCADE`。 |

### 4. 销售属性

| 表 | 作用与建表原因 |
|----|----------------|
| `sale_attr` | **销售属性字典**（如"版本""尺码"）。与平台属性不同，销售属性是 SKU 级的"销售维度"，作为字典表几乎不删。 |
| `sale_attr_value` | **销售属性值**（如"128G/256G""S/M/L"）。从属于某个 `sale_attr`，供 SKU 在销售属性维度上做组合。 |

### 5. SPU / SKU（商品核心）

| 表 | 作用与建表原因 |
|----|----------------|
| `spu` | **标准化产品单元**（如"iPhone 15"）。同一款商品的标准化描述，必须归属某个三级类目和品牌。SPU 是商品管理的"主记录"，其下挂图片列表与销售属性。 |
| `spu_image_list` | **SPU 图片列表**。SPU 的主图/详情图集合，从属于 SPU；SPU 删除后应随之一并清除（`CASCADE`）。 |
| `spu_sale_attr` | **SPU 销售属性定义**。描述某 SPU 支持哪些销售属性（引用 `sale_attr` 字典），是 SKU 销售属性组合的基础。 |
| `sku` | **库存量单元**（如"iPhone 15 256G 黑色"）。真正可售、有价格库存的最小单元，必须挂在某个 SPU 下，并冗余存储 `category3_id`/`tm_id` 用于详情页/列表直接读取、避免每次 join。 |
| `sku_image` | **SKU 图片**。SKU 级图片，从属于 SKU（`CASCADE`），并可引用 SPU 图（`SET NULL`，SPU 图删后 SKU 图置空不悬空）。 |
| `sku_attr_value` | **SKU 平台属性值关联**。把某个 SKU 与其拥有的平台属性值绑定，同时引用 `attr`/`attr_value` 约束"SKU 只能用已存在的属性/属性值"，拦截脏数据（`RESTRICT`）。 |
| `sku_sale_attr_value` | **SKU 销售属性值关联**。把 SKU 与其销售属性值（如"256G""黑色"）绑定，从属于 SKU（`CASCADE`）。 |

### 6. 权限域（RBAC）

| 表 | 作用与建表原因 |
|----|----------------|
| `users` | **系统用户/后台账号**。登录主体，含账号、密码、昵称、`status`（账号状态，`true`=正常、`false`=锁定）。`status` 用于"锁定/解锁账号"功能：锁定后登录直接拒绝（复用"用户名或密码错误"提示，不泄露账号状态）。 |
| `role` | **角色**（如"超级管理员""运营"）。权限的集合载体，解耦"用户"与"菜单权限"，便于批量授权。 |
| `menu` | **系统菜单/权限项**（对齐 MySQL 源结构，不含 `id` 自增主键，以 `id` 业务主键标识）。后台左侧菜单与可访问的接口权限，是 RBAC 的最小授权单元。 |
| `role_menu` | **角色-菜单关联**（多对多中间表）。记录"某角色拥有哪些菜单权限"，删角色/删菜单时关联记录自动清除（`CASCADE`）。 |
| `user_role` | **用户-角色关联**（多对多中间表）。记录"某用户拥有哪些角色"，删用户/删角色时关联记录自动清除（`CASCADE`）。 |

> 为什么用 `users ⟷ user_role ⟷ role ⟷ role_menu ⟷ menu`
> 五张表而不是直接给用户挂菜单？因为"角色"这层抽象让权限可复用：新增用户只需分配已有角色，无需逐个勾选菜单；调整某类人权限只需改角色，所有关联用户自动生效。

## 一、背景

原初始化脚本仅用 `DROP TABLE IF EXISTS` + `CREATE TABLE`
建表，表与表之间**没有任何外键约束**，引用完整性完全靠 Go 代码（如 `DeleteSpu`
手工"先子后父"删除）维护。这种方式有两个隐患：

1. **容易留孤儿数据**：一旦某处漏调子表清理逻辑，父子引用就断链。
2. **误删无兜底**：可以直接删掉一个仍被 SPU/SKU 引用的类目或品牌，导致下游数据悬空。

后台管理系统属于"一致性 > 灵活性"的场景，因此本次改造为**核心关联**补上外键，并配合
`ON DELETE RESTRICT` / `CASCADE` 策略。

## 二、DROP 语句改造（关键前提）

加外键后，重建表时若父表被子表引用，普通 `DROP TABLE` 会报"被外键引用，无法删除"。

**改法**：把每张表的

```sql
DROP TABLE IF EXISTS app.xxx;
```

统一改为

```sql
DROP TABLE IF EXISTS app.xxx CASCADE;
```

> 注意：`DROP TABLE ... CASCADE` 中的 CASCADE 是 **DDL
> 级**的——它只会**连带删除"引用该表的外键约束"这个元数据**，并不会删除任何业务数据（整张表本来就要 DROP 重建）。因此加了 CASCADE 后，DROP 的先后顺序就**不再受限**，脚本中"每张表 DROP 写在各自 CREATE 前"的原始结构可原样保留。

这与外键定义里的 `ON DELETE
CASCADE`（**数据级**，删父行时自动删子行）是**两件完全不同的事**，只是名字都叫 CASCADE。

## 三、如何判断父表 / 子表

外键语法固定为：

```sql
ALTER TABLE <子表>
  ADD CONSTRAINT <约束名>
  FOREIGN KEY (<子表里引用父的字段>)
  REFERENCES <父表> (<父表里被引用的字段>)
  ON DELETE <策略>;
```

### 铁律： 右边的是父表，左边  /  的是子表

以类目三级链为例：

```sql
ALTER TABLE app.category2
  ADD CONSTRAINT fk_category2_cat1
  FOREIGN KEY (category1_id) REFERENCES app.category1 (category1_id) ON DELETE RESTRICT;
```

- `ALTER TABLE app.category2` → **category2 是子表**（要加约束的这张）
- `FOREIGN KEY (category1_id) REFERENCES app.category1` → category2 的 `category1_id` 指向
  **category1（父表）**
- 含义：二级类目 category2 属于某个一级类目 category1，即"子指向父"

同理，`category3.category2_id REFERENCES category2` 中，category3 是子、category2 是父。

**父子命名比喻**：父表 = 被依赖、独立存在的那张（如 category1，不依赖谁）；子表 =
依赖父表才能存在的那张（如 category2，必须挂在一个 category1 下才有意义）。子表里的
`category1_id` 叫**外键列**，父表里被指的 `category1_id`（通常是主键）叫**被引用列**。

**辅助记忆**：本次约束命名统一为 `fk_<子表>_<父表简称>`（如 `fk_category2_cat1` = "category2 到
category1 的外键"），扫一眼名字即可知方向。

## 四、外键列索引说明

PostgreSQL
在创建外键时**不会自动为外键列建立索引**。如果某张子表的外键列需要索引（例如删除/更新父表时需回查子表、或按该列做高频查询），需要**手动 `CREATE INDEX`** 添加，外键本身不会代劳。

## 五、外键清单

外键统一追加在全部 `CREATE TABLE` 与触发器之后，避免建表时引用尚未存在的父表。

### 1. 类目三级链（RESTRICT：禁止删有子项的父项）

**为什么**：商品类目是三级树形结构（一级 → 二级 →
三级），下级必须挂在存在的上级之下。一个一级类目下若还有二级、三级类目或商品，绝不允许被直接删掉，否则下级数据全部悬空。用 `RESTRICT` 强制"先清理下级再删上级"。

| 子表 | 字段 | 引用父表 | 关系含义 | 删除策略 |
|------|------|----------|----------|----------|
| `category2` | `category1_id` | `category1` | 二级类目属于某个一级类目 | RESTRICT |
| `category3` | `category2_id` | `category2` | 三级类目属于某个二级类目 | RESTRICT |

### 2. 平台属性

**为什么**：平台属性（如"颜色""内存"）挂在某个**三级**类目下（页面要求选到三级分类才能添加属性），属性值又从属于具体属性——`attr` 表存"属性维度"（颜色只定义一次），`attr_value` 表存"具体选项"，靠 `attr_value.attr_id` 指向所属属性；**同一个 `attr_id` 可重复出现多次，正是"一个属性有多种值"的体现（如手机"颜色"属性下有白色/黑色/金色三行值）**。属性被删时，其下的属性值没有存在意义，应一并清除（`CASCADE`）；但类目下若已定义属性，则不能随便删类目（`RESTRICT`）。

| 子表 | 字段 | 引用父表 | 关系含义 | 删除策略 |
|------|------|----------|----------|----------|
| `attr` | `category_id` | `category3` | 平台属性归属于某个三级类目 | RESTRICT |
| `attr_value` | `attr_id` | `attr` | 属性值从属于某个属性 | CASCADE |

### 3. SPU / SKU 主链

**为什么**：SPU（标准化产品，如"iPhone
15"）必须挂在某个三级类目和品牌下；SKU（具体库存单元，如"iPhone 15 256G
黑色"）必须挂在某个 SPU 下。删 SPU 时其下所有 SKU
自然失效，应级联删除（`CASCADE`）；但类目/品牌若仍有商品引用就不能删（`RESTRICT`），否则商品找不到归属。

| 子表 | 字段 | 引用父表 | 关系含义 | 删除策略 |
|------|------|----------|----------|----------|
| `spu` | `category3_id` | `category3` | SPU 归属三级类目 | RESTRICT |
| `spu` | `tm_id` | `trademark` | SPU 归属品牌 | RESTRICT |
| `sku` | `spu_id` | `spu` | SKU 从属于某个 SPU | CASCADE |
| `sku` | `category3_id` | `category3` | SKU 归属三级类目 | RESTRICT |
| `sku` | `tm_id` | `trademark` | SKU 归属品牌 | RESTRICT |

### 4. SPU 从表

**为什么**：SPU 的图片列表、销售属性都是从属于 SPU 的附属数据，SPU
删除后这些从表数据毫无意义，应随 SPU 级联删除（`CASCADE`），对应代码中 `DeleteSpu`
手工"先子后父"的清理逻辑。

| 子表 | 字段 | 引用父表 | 关系含义 | 删除策略 |
|------|------|----------|----------|----------|
| `spu_image_list` | `spu_id` | `spu` | SPU 的图片列表 | CASCADE |
| `spu_sale_attr` | `spu_id` | `spu` | SPU 的销售属性 | CASCADE |

### 5. SKU 从表

**为什么**：SKU 的图片、平台属性值关联、销售属性值关联都是从属于 SKU 的附属数据，SKU
删除后应一并清除（`CASCADE`）。而其中 `sku_attr_value` 同时引用平台属性 `attr` 与属性值
`attr_value`——这层引用是为了约束"SKU 只能使用已存在的属性/属性值"，防止脏数据，故用
`RESTRICT`（属性被引用时禁止删）。

| 子表 | 字段 | 引用父表 | 关系含义 | 删除策略 |
|------|------|----------|----------|----------|
| `sku_image` | `sku_id` | `sku` | SKU 的图片 | CASCADE |
| `sku_attr_value` | `sku_id` | `sku` | SKU 的平台属性值关联 | CASCADE |
| `sku_attr_value` | `attr_id` | `attr` | 关联所用平台属性 | RESTRICT |
| `sku_attr_value` | `attr_value_id` | `attr_value` | 关联所用属性值 | RESTRICT |
| `sku_sale_attr_value` | `sku_id` | `sku` | SKU 的销售属性值关联 | CASCADE |
| `sku_sale_attr_value` | `sale_attr_value_id` | `sale_attr_value` | 关联所用销售属性值 | CASCADE |

### 6. RBAC 关联

**为什么**：系统用 `users ⟷ user_role ⟷ roles ⟷ role_menu ⟷ menu`
五张表实现"用户-角色-菜单"权限模型。关联表（user_role /
role_menu）本身只是关系，父表（用户/角色/菜单）被删时，其关联记录已无意义，应级联清除（`CASCADE`）。这样删一个角色会自动撤销该角色对所有菜单的授权、以及所有用户对该角色的拥有关系。

| 子表 | 字段 | 引用父表 | 关系含义 | 删除策略 |
|------|------|----------|----------|----------|
| `role_menu` | `role_id` | `role` | 角色拥有的菜单权限 | CASCADE |
| `role_menu` | `menu_id` | `menu` | 菜单被哪些角色授权 | CASCADE |
| `user_role` | `user_id` | `users` | 用户拥有的角色 | CASCADE |
| `user_role` | `role_id` | `role` | 角色被哪些用户拥有 | CASCADE |

### 未加外键的关联（刻意保留）

- `sale_attr_value.sale_attr_id →

  sale_attr`：**为什么不加**——`sale_attr`（颜色/版本/尺码）是**字典表，几乎不删**，且 seed
  已写入固定数据。若加外键，日后新增销售属性值要先动字典，反而受限，故暂不添加，保持字典灵活性。

## 五·之一、外键必要性分级

本项目所有外键并非"为加而加"，按其必要性可分为三类。理解分级有助于后续 Review
时判断"某条外键能不能删"。

### A 类：强必要（模型本身存在父子依赖，不加会留孤儿数据）

删父类目/SPU/SKU/属性时，若无外键约束，子表会沦为悬空引用（指向不存在的父）。**必须加**。

| 外键 | 作用 |
|------|------|
| `fk_category2_cat1` / `fk_category3_cat2` | 类目三级链，删父类目必须拦子，否则悬空 |
| `fk_spu_cat3` / `fk_spu_tm` | SPU 必须归属真实存在的三级类目/品牌 |
| `fk_spu_img_spu` / `fk_spu_sale_attr_spu` | SPU 从表，删 SPU 级联清子 |
| `fk_sku_img_sku` / `fk_sku_attr_val_*` / `fk_sku_sale_av_*` | SKU 从表，删 SKU 级联清子 |
| `fk_attr_value_attr` | 属性值依赖属性，删属性级联清值 |

### B 类：防御性必要（模型允许、业务上几乎不发生，加了零副作用、能堵脏值）

字典类引用，业务上字典几乎不删，加 `RESTRICT` 无副作用，却能拦截"写入不存在的引用
ID"的脏数据。**建议加**。

| 外键 | 作用 |
|------|------|
| `fk_attr_cat3` | 属性必须挂在真实三级类目，杜绝传错级别/乱写 ID（本轮由 `fk_attr_cat1` 修正而来） |
| `fk_spu_sale_attr_base` | SPU 销售属性必须引用真实字典项，堵 `base_sale_attr_id=999` 脏值 |
| `fk_sku_img_spi` | SKU 图引用 SPU 图，SET NULL 避免悬空（SPU 图删后 SKU 图置空） |

### C 类：反范式冗余列上的外键（按业务选择保留）

`sku` 表冗余存储了 `category3_id` / `tm_id`（详情页/列表直接读，避免每次 join
`spu`）。这两列本身非范式必须，但既然保留，**外键也应保留**，以保证冗余列里的值也指向真实类目/品牌、不自相矛盾。

| 外键 | 作用 |
|------|------|
| `fk_sku_cat3` / `fk_sku_tm` | 保证 `sku` 冗余列的值指向真实三级类目/品牌 |

> 备注：若日后将冗余列改为走
> A（彻底去冗余、删这两列），则这两条外键会随列一起删除；当前选定 B，故保留。

## 六、删除策略：CASCADE 与 RESTRICT 的区别

外键的 `ON DELETE` 策略决定**删除父表行时，子表引用行如何处理**。两种策略的核心区别：

- **`CASCADE`（级联）**：删父行时，**自动把子表里引用它的行也一起删掉**，一行命令搞定。
- **`RESTRICT`（限制）**：只要子表里还有行引用它，**直接拒绝删除并报错**，必须先手动清掉子表数据，才能删父。

同一个"删 SPU（其下有 5 个 SKU）"的动作，两种结果：

| 策略 | `DELETE FROM spu WHERE spu_id=100` 的结果 |
|------|------|
| `ON DELETE CASCADE` | SPU 删掉，**底下 5 个 SKU 也被自动删掉** |
| `ON DELETE RESTRICT` | **报错拒绝**："仍有 SKU 引用该 SPU"，须先手动删光 5 个 SKU 才能删 SPU |

> 注意：无论哪种策略，**删子表本身都不受约束**——外键只管"父被删时子怎么办"，删子表时父表留着不动完全合法。

**选择经验法则**：父删了对子没意义（从表附属数据、授权关系）→ 用
`CASCADE`，省心；父被引用时不能随便消失（类目、品牌、字典）→ 用 `RESTRICT`，防事故。

### 本项目的具体设计意图

- **`ON DELETE RESTRICT`**：用于类目链、`trademark`、`attr`、RBAC
  的父表等。目的是**防止误删**——想删一个仍被引用的一级类目 / 品牌 /
  角色时，数据库直接拒绝，强制你先清理子数据。这正好规避"手滑删大类目连带清光商品"的事故。
- **`ON DELETE CASCADE`**：用于 SPU/SKU 的从表及 RBAC 关联表。删父即自动连带清子，和代码里

  `DeleteSpu` 等手工"先子后父"逻辑一致——本项目用 CASCADE
  也是为了与既有删除代码双保险。

## 七、对业务代码的影响

1. **`DeleteSpu` 可简化但非必须**：`spu_image_list` / `spu_sale_attr` 已设为 `ON DELETE
   CASCADE`，代码里手工删这三张表的逻辑可以保留（不报错）或删掉（交给数据库级联）。建议保留，避免改出回归。
2. **删 `category1` / `trademark` / `role` 会被 RESTRICT
   拦住**：必须先清子数据，否则收到外键违规错误。后端需在 service 层捕获
   `foreign_key_violation` 并给出友好提示。
3. **级联副作用须知**：删一个 `spu`，其下所有 `sku` 也会被级联删除（因为 `sku.spu_id → spu`
   是 CASCADE）。这是业务合理的，但运维删数据时需知晓。
4. **seed 不受影响**：seed 由 Go 代码运行，在 init-sql

   之后；它先建父（category/trademark/role/menu）再建子（sku/spu/关联），配合外键完全兼容。

## 八、账号锁定（users.status）

`users` 表新增 `status boolean NOT NULL DEFAULT true`，用于"锁定/解锁账号"：

- `true` = 正常（默认），`false` = 锁定。
- 登录时若 `status =
  false`，直接拒绝登录（复用"用户名或密码错误"提示，不泄露账号状态）。
- 提供 `POST /api/v1/acl/user/lock` 接口（`ParamUserLock{ UserID, Status }`）动态锁定/解锁，由
  `repository.LockUser` 更新该列。
- 应用层写入恒为 `true` 指针或经 `derefBool` 解引用，从不写 NULL，与 `NOT NULL` 约束一致；seed

  不写该列时走 `DEFAULT true`。

## 九、回滚方式

若需撤销外键，执行对应的 `DROP CONSTRAINT` 即可，例如：

```sql
ALTER TABLE app.sku DROP CONSTRAINT fk_sku_spu;
ALTER TABLE app.role_menu DROP CONSTRAINT fk_role_menu_role;
-- ... 其余同理
```

或直接使用带 `CASCADE` 的 `DROP TABLE` 重建（见第二节）。
