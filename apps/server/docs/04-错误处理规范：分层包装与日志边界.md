# 错误处理规范：分层包装与日志边界

本项目采用经典分层架构（handler → service → repository），错误在层与层之间向上传递。
本文规定**每一层对错误负什么责**：谁包装语义、谁打日志、
谁决定业务码、谁只做透传。
配套文档见《统一 HTTP 返回格式：从"能跑就行"到"网关级容错"的演进》
（只讲响应体，本文讲响应体之下的错误流转）。

---

## 一、三层职责边界（铁律）

| 层 | 对错误的职责 | 是否打印 | 是否带业务码 |
| --- | --- | --- | --- |
| **repository** | 用 `fmt.Errorf("动作(步骤): %w", err)` 包**精确步骤语义** | 否 | 否 |
| **service** | 打印一次并 `errs.Wrap(code, err)` 加业务码 | 是（唯一打印点） | 是 |
| **handler** | 只调用 `result.Error(c, errs.CodeOf(err))` 映射码 | 否（防重复打印） | 只映射 |

> **核心原则：整条链路只有 service 这一层打印日志。**
> 若 service 也只返回不打印，错误将无人记录；若 handler
> 再打印一次，就是双重打印、日志噪音。

---

## 二、repository 层：只包"精确步骤"，不带业务码

repo 是多个 service 共享的薄数据层，它**最清楚当前正卡在哪一步 DB 操作上**，
因此由它负责把"具体步骤"写进错误文本最精准。

### 2.1 单操作 vs 多操作的包装原则

- **单 DB 操作的函数**：直接 `return err`（裸 error），**不包装**。
  理由：步骤语义在 service 层通过函数名 + `slog` 上下文已能体现，repo 再包一层是冗余。
- **多 DB 操作**（或 DB + bcrypt/计数等混合操作）的函数：每个 `return err` 都用

  `fmt.Errorf("整体动作(具体步骤): %w", err)` 包一层，**精确区分到底是哪一步挂了**。

`%w` 保留底层 error，供上层 `errs.Wrap` / `errors.Is` / `errors.As` 透传与提取。

### 2.2 反例 vs 正例

#### 多操作函数（如属性更新：改属性名 + 改属性值 + 新建属性值 + 删过期属性值）

```go
// ❌ 反例：末尾裸 return err，日志里看不到具体哪一步失败
func (d *AttrRepo) UpdateAttrAndAttrValue(attr *model.Attr, values []*model.AttrValue) (err error) {
    _, err = d.q.Attr.WithContext(ctx).Where(d.q.Attr.AttrID.Eq(attr.AttrID)).
        Updates(map[string]any{"attr_name": attr.AttrName})
    if err != nil {
        return err               // 只知道"更新失败"，不知道是更新属性名还是属性值
    }
    // ... 后续还有 3 个 DB 操作 ...
    return err
}

// ✅ 正例：每一步都包"整体动作(具体步骤)"
func (d *AttrRepo) UpdateAttrAndAttrValue(attr *model.Attr, values []*model.AttrValue) (err error) {
    _, err = d.q.Attr.WithContext(ctx).Where(d.q.Attr.AttrID.Eq(attr.AttrID)).
        Updates(map[string]any{"attr_name": attr.AttrName})
    if err != nil {
        return fmt.Errorf("更新属性失败(更新属性名): %w", err)
    }
    // ... 循环里 ...
    if err != nil {
        return fmt.Errorf("更新属性失败(更新属性值): %w", err)
    }
    // ... 新建属性值 ...
    if err != nil {
        return fmt.Errorf("更新属性失败(新建属性值): %w", err)
    }
    // ... 删除过期属性值（最后一步从裸 return 改为单独判断）...
    if err != nil {
        return fmt.Errorf("更新属性失败(删除过期属性值): %w", err)
    }
    return nil
}
```

#### 单操作函数（如按 ID 查询）保持裸返回

```go
func (d *AttrRepo) GetAttr(c1Id, c2Id, c3Id int64) (data []*model.Attr, err error) {
    rows, err := d.q.Attr.WithContext(ctx).Where(d.q.Attr.CategoryID.Eq(c3Id)).Find()
    if err != nil {
        return nil, err           // 单操作，不包；步骤语义由 service 体现
    }
    return rows, nil
}
```

### 2.3 业务哨兵错误（sentinel error）不包

repo 内部用于表示"业务冲突"的哨兵错误
（如 `ErrorMenuExist`、`ErrorUserNotExist`、`ErrorRoleExist`、`ErrorTrademarkExist`）
是**有意返回的业务判定**，不应再用 `fmt.Errorf` 包，
直接 `return ErrorXxx` 即可，让 service 层按业务码映射。

## 三、service 层：唯一打印点 + 加业务码

service 是错误真正发生的边界：它把 repo 的"步骤文本"升级为"带业务码的可观测错误"。

```go
func (a *attrService) UpdateAttr(p *types.Attr) (err error) {
    attr := &model.Attr{AttrID: idconv.ToInt64Safe(p.AttrID), AttrName: p.AttrName}
    // ...
    err = a.repo.UpdateAttrAndAttrValue(attr, values)
    if err != nil {
        // ① 打印一次：日志文案写业务口语，并带顶层上下文（attr_id 等）
        slog.Error("更新属性失败",
            slog.Int64("attr_id", attr.AttrID),
            slog.Any("error", err))            // err 里已含 repo 的"具体步骤"
        // ② 加业务码后向上返回
        return errs.Wrap(result.CodeAttrDBErr, err)
    }
    return err
}
```

要点：

1. **打印文案用业务口语**（如"更新属性失败"），不要写
   `repository.AttrRepo.UpdateAttrAndAttrValue() failed` 这种函数名风格——
   具体步骤已由 repo 的 `fmt.Errorf` 带进 `err` 里了。
2. `slog.Any("error", err)` 会把完整的错误链打出来：
   `更新属性失败(删除过期属性值): *pq.Error ...`。
3. `errs.Wrap(code, err)` 只加业务码，不破坏底层错误链

   （`BizError.Unwrap()` 透传）。

### 3.1 `errs` 包核心 API（`pkg/errs/errs.go`）

```go
// 把底层 error 包装为带业务码的错误；err 为 nil 时返回 nil
func Wrap(code result.ResCode, err error) error

// 从 error 中提取业务码：nil→成功码；*BizError→其码；其他裸/sentinel→CodeServerBusy
func CodeOf(err error) result.ResCode

// BizError 携带 Code 与底层 Err，实现 Error()+Unwrap()，便于 errors.As/Is 透传
type BizError struct {
    Code result.ResCode
    Err  error
}
```

## 四、handler 层：只映射码，不打印

```go
func (h *AttrHandler) UpdateAttr(c *gin.Context) {
    // ... 绑定参数 ...
    if err := h.svc.UpdateAttr(p); err != nil {
        result.Error(c, errs.CodeOf(err))   // 只映射错误码，不打印
        return
    }
    result.Success(c, nil)
}
```

## 五、最终错误链长什么样

以「属性更新时删除过期属性值这步失败」为例，错误从底到顶是：

```text
BizError{
    Code: CodeAttrDBErr,                                  // service 加的业务码
    Err:  更新属性失败(删除过期属性值): *pq.Error{...}     // repo 包的步骤语义 + 底层驱动错误
}
```

- **日志**（service 打印一次）：
  `level=ERROR msg="更新属性失败" attr_id=123 error="更新属性失败(删除过期属性值): ..."`
- **响应体**（handler 映射）：

  `{"code": 120101, "message": "属性操作失败", "data": null}`
  业务码对应的静态文案在 `pkg/result/codeMsgMap` 中定义，详见统一 HTTP 返回格式文档。

最终效果：日志里既能看**业务意图**（更新属性）、
又能看**具体步骤**（删除过期属性值）、
还能看**底层原因**（pq 驱动错误）；响应体只暴露业务码与脱敏文案。

## 七、约定速查（新增 repo 函数时）

1. 函数里**只有 1 个 DB 操作** → 直接 `return err`，不包装。
2. 函数里**有多个 DB 操作** → 每个 `return err` 用
   `fmt.Errorf("整体动作(具体步骤): %w", err)`。
3. **业务哨兵错误**（如 `ErrorXxxExist`）→ 直接 `return ErrorXxx`，不包。
4. repo **绝不打印日志、绝不决定业务码**。
5. service 在 repo 边界处**必须** `slog.Error(...)` 一次
   （业务口语 + 顶层上下文）并 `errs.Wrap(code, err)`。
6. handler **只** `result.Error(c, errs.CodeOf(err))`，不打印。
