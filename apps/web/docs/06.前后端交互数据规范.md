# 06. 前后端交互数据规范

## 一、总体原则（铁律）

1. **前端面向业务**：使用人类可读的业务单位（元、克、厘米、毫升）。
2. **后端面向存储**：使用最小整数单位（分、毫克、微米、微升）。
3. **API 层是唯一转换边界**：前端提交时转一次，后端返回时转一次，其余地方透明。
4. **字段名必须自带单位后缀**：拒绝魔法数字，拒绝隐式契约。
5. **ID 优先用字符串**：防止 JavaScript `Number` 精度丢失（通用最佳实践）。⚠️ **本仓库特例**：后端 `id` 为 `int64` 且 JSON 输出 `number`（数据量小、无精度风险），前端 TS 中 `id` 声明为 `number`。
6. **时间只用 RFC3339**：消灭时区歧义。
7. **命名约定（前后端统一 camelCase）**：
   - 后端 JSON 字段与前端 TS 接口**统一使用 camelCase**（如 `priceCent`、`weightMg`、`menuId`、`parentId`、`spuId`、`skuId`）。
   - 前后端直接对齐同一套字段名，不再做 snake_case ↔ camelCase 映射，**请求层与业务代码均不关心键名差异**。
   - **前端发出的就是分、毫克等最小整数单位**（整数），不是业务单位。例如 `priceCent: yuanToCent(form.priceYuan)` 提交的值已是 `899900`（分）。

## 三、单位换算关系表

| 物理量 | 业务单位 → 最小单位 | 换算系数 | 字段名后缀 (camelCase) | 前端字段       | 前端小数位 | 精度说明          |
| :----- | :------------------ | :------- | :--------------------- | :------------- | :--------- | :---------------- |
| 金额   | 元 → 分             | × 100    | `Cent`                 | `priceCent`    | 2 位       | 人民币最小单位    |
| 重量   | 克 → 毫克           | × 1000   | `Mg`                   | `weightMg`     | 3 位       | 物理世界极限精度  |
| 长度   | 厘米 → 微米         | × 10000  | `Um`                   | `lengthUm`     | 4 位       | 精密制造/物流需求 |
| 面积   | cm² → µm²           | × 10⁸    | `Um2`                  | `areaUm2`      | 8 位       | 由长×宽动态计算   |
| 体积   | 毫升 → 微升         | × 1000   | `Ul`                   | `volumeUl`     | 3 位       | 液体/容积场景     |
| 密度   | g/ml → ratio        | × 1000   | `Ratio`                | `densityRatio` | 3 位       | 放大整数存储      |

## 四、后端约定（要点）

> 本仓库为前端工程，以下仅列出与前端契约相关的后端要点，不展开实现细节。

- **JSON 输出统一 camelCase**：所有对外字段与前端 TS 同名（如 `priceCent`、`weightMg`、`menuId`），DB 列名内部可用 snake_case，但 JSON 输出仍为 camelCase，不做键名映射。
- **计量字段用最小整数单位**：金额 `priceCent`（分）、重量 `weightMg`（毫克）、长度 `lengthUm`（微米）等。
- **时间字段**：`createTime` / `updateTime` 输出 RFC3339，零值时省略（不返回 `0001-01-01T00:00:00Z`）。
- **ID 约定**：所有 ID 以字符串返回（DB 主键 `int64`），避免 JS `Number` 精度丢失；请求 DTO 与响应 VO 字段名一致，DO ↔ VO 转换在后端内部完成，前端只关心 JSON 字段名。

### 5.2 单位转换工具库（核心）

```typescript
// utils/unit.ts

// ============================================================
// 金额
// ============================================================

/**
 * 元 → 分（提交用）
 * @example yuanToCent(19.99) → 1999
 * 必须用 Math.round 而非 Math.floor/parseInt：浮点误差会使 0.29*100 = 28.999999999999996，
 * Math.round 得到 29（正确），Math.floor 会得到 28（错误）。所有「业务单位 → 最小单位」函数同理。
 */
export const yuanToCent = (yuan: number): number => {
  if (isNaN(yuan) || yuan < 0) throw new Error('金额不合法')
  return Math.round(yuan * 100)
}

/**
 * 分 → 元（展示用）
 * @example centToYuan(1999) → "19.99"
 */
export const centToYuan = (cent: number): string => {
  return (cent / 100).toFixed(2)
}

// ============================================================
// 重量
// ============================================================

/**
 * 克 → 毫克（提交用）
 * @example gramToMg(192.43) → 192430
 */
export const gramToMg = (g: number): number => {
  if (isNaN(g) || g < 0) throw new Error('重量不合法')
  return Math.round(g * 1000)
}

/**
 * 毫克 → 克（展示用）
 * @example mgToGram(192430) → "192.430"
 */
export const mgToGram = (mg: number): string => {
  return (mg / 1000).toFixed(3)
}

// ============================================================
// 长度
// ============================================================

/**
 * 厘米 → 微米（提交用）
 * @example cmToUm(15.5) → 155000
 */
export const cmToUm = (cm: number): number => {
  if (isNaN(cm) || cm < 0) throw new Error('长度不合法')
  return Math.round(cm * 10000)
}

/**
 * 微米 → 厘米（展示用）
 * @example umToCm(155000) → "15.5000"
 */
export const umToCm = (um: number): string => {
  return (um / 10000).toFixed(4)
}

// ============================================================
// 体积
// ============================================================

/**
 * 毫升 → 微升（提交用）
 * @example mlToUl(95.625) → 95625
 */
export const mlToUl = (ml: number): number => {
  if (isNaN(ml) || ml < 0) throw new Error('体积不合法')
  return Math.round(ml * 1000)
}

/**
 * 微升 → 毫升（展示用）
 * @example ulToMl(95625) → "95.625"
 */
export const ulToMl = (ul: number): string => {
  return (ul / 1000).toFixed(3)
}

// ============================================================
// 密度
// ============================================================

/**
 * g/ml → ratio（提交用，放大 1000 倍）
 * @example densityToRatio(1.04) → 1040
 */
export const densityToRatio = (density: number): number => {
  if (isNaN(density) || density <= 0) throw new Error('密度不合法')
  return Math.round(density * 1000)
}

/**
 * ratio → g/ml（展示用）
 * @example ratioToDensity(1040) → "1.040"
 */
export const ratioToDensity = (ratio: number): string => {
  return (ratio / 1000).toFixed(3)
}

// ============================================================
// 时间
// ============================================================

/**
 * Date 对象 → RFC3339 字符串（提交用）
 * ⚠️ date.toISOString() 永远输出 UTC 时间（带 Z 后缀），与浏览器时区无关。
 * 约定：提交统一用 toISOString()（UTC 时刻），展示用 formatDateTime()（本地时区）转回。
 * 两者基于同一时刻，不会丢精度；切勿混用 toLocaleString() 提交，否则会产生时区漂移。
 * @example dateToRFC3339(new Date()) → "2026-01-15T00:30:00.000Z"
 */
export const dateToRFC3339 = (date: Date): string => {
  return date.toISOString()
}

/**
 * RFC3339 → 本地时间字符串（展示用）
 * @example formatDateTime("2026-01-15T08:30:00Z") → "2026/1/15 16:30:00"
 */
export const formatDateTime = (isoString: string): string => {
  return new Date(isoString).toLocaleString()
}
```

### 5.3 表单提交示例（Vue3）

```vue
<template>
  <!-- 表单用业务单位（元/克/cm），提交时转换一次 -->
  <el-form-item label="售价 (元)">
    <el-input v-model.number="form.priceYuan" type="number" :step="0.01" />
  </el-form-item>
  <!-- 展示区用最小单位还原业务单位 -->
  <p>售价: {{ centToYuan(product.priceCent) }} 元</p>
</template>

<script setup lang="ts">
import { reactive } from 'vue'
import { productApi } from '@/api/product'
import { yuanToCent, centToYuan } from '@/utils/unit'

const form = reactive({ priceYuan: 8999.0 })
const product = reactive({ priceCent: 0 })

const handleSubmit = async () => {
  // 提交字段名与后端统一 camelCase，值已是最小整数单位（分）
  const payload = {
    skuId: 'SKU_001',
    name: 'iPhone 15 Pro',
    priceCent: yuanToCent(form.priceYuan), // 8999 元 → 899900 分
    weightMg: gramToMg(form.weightGram), // 其余计量字段同理
  }
  const res = await productApi.create(payload)
  Object.assign(product, res.data) // res.data 字段已是 camelCase
}
</script>
```

### 5.4 列表 / 批量场景（重要）

- **列表项同样只存最小单位**：`Product` 接口是单条也是列表项（`records: Product[]`），数据进 Pinia / 组件 `ref` 时**保持 `priceCent` 等最小单位整数**，不要提前转成元。
- **转换只在模板里做**：渲染时调用展示函数 `centToYuan(item.priceCent)`，编辑回填表单时再 `yuanToCent(form.priceYuan)` 转回。这样 store 里永远是权威的最小单位，二次编辑不丢精度。
- **禁止**把 `centToYuan(...)` 的结果写回 store（会变成 `string`，丢失整数精度且无法再精确编辑）。

```typescript
// ✅ 正确：store 里存最小单位，模板里展示时转换
const list = ref<Product[]>([])
// 模板：{{ centToYuan(item.priceCent) }} 元

// ❌ 错误：把转换结果存进 store
list.value = res.data.records.map((i) => ({ ...i, priceCent: centToYuan(i.priceCent) }))
```

## 六、API 接口示例

### 6.1 创建商品

**Request:**

```http
POST /api/v1/products
Content-Type: application/json
```

```json
{
  "skuId": "SKU_IPHONE_15_PRO",
  "name": "iPhone 15 Pro",
  "priceCent": 899900,
  "weightMg": 187000,
  "lengthUm": 147600,
  "widthUm": 70600,
  "heightUm": 8300,
  "volumeUl": 86500,
  "densityRatio": 2165
}
```

**Response:**

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "id": 1893128372123456,
    "skuId": "SKU_IPHONE_15_PRO",
    "name": "iPhone 15 Pro",
    "priceCent": 899900,
    "weightMg": 187000,
    "lengthUm": 147600,
    "widthUm": 70600,
    "heightUm": 8300,
    "volumeUl": 86500,
    "densityRatio": 2165,
    "createTime": "2026-01-15T10:30:00Z",
    "updateTime": "2026-01-15T10:30:00Z"
  }
}
```

> 说明：字段名与前端 TS 完全一致（camelCase，不做键名映射）；所有计量值已是最小整数单位（`899900` 为分，`187000` 为毫克）；`code` 为 `200` 表示成功（非 `0` 也非 `20000`），且 HTTP 状态恒为 200；`id` 为 `number`（本仓库 `int64` 直接输出数字）。

### 6.2 通用响应结构

> **统一响应结构**：所有接口返回包裹对象 `{ code, data, message }`，由前端 `axios` 拦截器统一处理（`src/utils/request.ts` 配合 `src/types/api.d.ts` 生成的 `ResponseData<T>`）。
>
> - **成功**：`code === 200`，拦截器返回 `res.data`，页面直接取业务数据。
> - **鉴权失败**：`code === 110002`（未登录）/ `110003`（token 失效），拦截器清空 token 并跳转登录页。
> - **其他业务错误**：`code` 为其它非 200 值，拦截器 `ElMessage` 提示 `message` 后 reject。
> - ⚠️ **所有响应 HTTP 状态恒为 200**，务必解析响应体 `code` 字段，不要依赖 HTTP 状态码。
> - `data` 为业务数据（**分页接口里 `data` 即 `{ records, total, ... }` 等业务结构，不再额外包顶层 `meta` / `ok` 字段**）。字段名 camelCase，与 swagger 一致，前后端不做键名映射。

## 八、数值范围安全验证

> JavaScript `Number` 最大安全整数：`9,007,199,254,740,991` (2^53 - 1)

| 字段           | 单位       | 实际最大值 | 对应业务值              | 安全？ |
| :------------- | :--------- | :--------- | :---------------------- | :----- |
| `priceCent`    | 分         | 9×10¹⁵     | 9×10¹³ 元（90 万亿）    | ✅     |
| `weightMg`     | 毫克       | 9×10¹⁵     | 9×10⁹ kg（900 万吨）    | ✅     |
| `lengthUm`     | 微米       | 9×10¹⁵     | 9×10⁷ m（9 万公里）     | ✅     |
| `volumeUl`     | 微升       | 9×10¹⁵     | 9×10⁹ m³（90 亿立方米） | ✅     |
| `densityRatio` | ratio×1000 | 9×10¹⁵     | 9×10¹² g/ml             | ✅     |

👉 **在电商/物流业务范围内，所有计量字段都不会触碰 JS 精度上限。**

## 附录 B：常见 Q&A

**Q1: 为什么不用 `decimal` 类型？**  
A: 整数方案零依赖、性能最好、序列化最简单。只有金融/支付场景才需要 `decimal`。

**Q2: 前端计算总价怎么办？**  
A: 所有涉及金额的计算（加减乘除、税费、优惠）必须在后端完成，前端只做展示。

**Q3: 为什么长度用微米而不是毫米？**  
A: 物流和精密制造中 0.1mm 的误差有时是致命的，微米能覆盖更多场景。如果业务只用到毫米，可改为 `Mm`，系数改为 1000。

**Q4: 面积要不要单独存？**  
A: 不建议。面积通过 `lengthUm × widthUm` 动态计算即可，单独存容易不一致。
