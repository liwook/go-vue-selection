# 04. 路由守卫与动态权限路由实现（手把手执行文档）

> 在「静态路由表 + Layout + 递归菜单」骨架上接**鉴权路由**：未登录访问任意页跳 `/login`；登录后按用户 `routes` 动态挂菜单（管理员看全部，普通用户只看商品管理）；刷新权限不丢。
>
> 涉及文件：`router/routes.ts`（拆 `asyncRoutes`/`anyRoute`）、`utils/routeFilter.ts`（新增，递归过滤）、`store/modules/user.ts`（token/用户信息/动态菜单）、`router/index.ts`（`beforeEach` 守卫）、`utils/request.ts`（注入 token）、`views/login/index.vue`（登录页）。

---

## 步骤 0：先想清楚数据怎么流（必读，避免改错）

```bash
登录页填账号密码
  └─> userStore.userLogin(form)  ──> POST /api/v1/acl/index/login 拿到 data.token
        └─> token 存 pinia + localStorage('TOKEN')
        └─> 跳转 redirect || '/'

路由守卫 beforeEach
  └─> 有 token？
       ├─ 无 token 且不是 /login  ──> 跳 /login?redirect=当前路径
       ├─ 有 token 且去 /login   ──> 重定向到 /
       └─ 有 token 且去其他页：
             ├─ 已加载过用户信息（userStore.userInfo.name 有值）→ 直接 next()
             └─ 没加载过 ──> await userStore.getUserInfo()
                   ├─ 成功：filterAsyncRoute 算出菜单 + router.addRoute 动态挂载
                   │         └─> next({ ...to, replace: true })  // 关键：重新解析一次
                   └─ 失败：logout 清 token，跳 /login
```

**关键点**：动态路由必须在「拿到用户信息之后」用 `router.addRoute` 挂上去，挂完要 `next({...to, replace:true})` 让路由重新匹配一次，否则首次进动态页面会是白屏/404。

## 步骤 1：拆分 `src/router/routes.ts`

把现在的「全部静态」拆成三块。

> **为什么拆三块？**
>
> - `constantRoutes`：不需要权限的页面（登录、首页、大屏、404 页）。任何人都能进，一开始就注册进 router。
> - `asyncRoutes`：需要权限的页面（权限管理、商品管理）。**不能一开始就注册**，否则没登录也能直接访问。登录后按用户权限用 `router.addRoute` 挂上。
> - `anyRoute`：404 兜底通配。**必须放最后 addRoute**。如果它留在 `constantRoutes` 里，会在动态路由之前把所有未知路径直接重定向到 /404，导致动态页面进不去。
>   **为什么父路由（/acl、/product）这里不给 `name`？**
>   因为本方案的过滤逻辑是「父路由只要还有存活的子项就保留」（见步骤 2），父路由本身不参与名字匹配，所以不需要 `name`。子路由的 `name`（`user`/`role`/...）才是过滤的依据，必须保留。
>   （对比另一种写法：让父路由也出现在后端 `routes` 列表里，那父路由就得有 `name`。本方案更干净——父路由纯粹是个容器，不该为了「被保留」而硬塞进权限列表。）

## 步骤 2：新增 `src/utils/routeFilter.ts`

> **为什么需要这个函数？**
> 你 `asyncRoutes` 里写的是「系统总共能有哪些页面」（acl 下 user/role/permission，product 下 attr/spu/sku/trademark）。但不同用户该看的不同——普通用户不该看到「权限管理」。如果不裁，只有两种糟糕结果：① 全量 `addRoute` → 权限失效（谁都能进）；② 不 `addRoute` → 功能全废（谁都进不了）。这函数就是那把「剪刀」：拿后端返回的「能看名单」(`routes`)，去完整路由表里把对不上的枝叶剪掉，产出「当前用户专属的路由树」。它同时喂给两处：① `menuRoutes`（菜单只显示能看的）② `router.addRoute`（只能进能看的页）。前端只定义「有哪些能力」，后端决定「谁有哪个」——函数就是连接这两头的桥梁。
>
> 过滤规则：父路由（`/acl`、`/product`）是容器，只要还有存活子项就保留（故父路由无需 `name`）；叶子路由看 `name` 是否在后端列表里（用 `name` 而非 `path`，因 `path` 混相对/绝对易错）。细节见下方代码注释。

```ts
import type { RouteRecordRaw } from 'vue-router'

/**
 * 根据后端返回的 routes（路由名数组）过滤异步路由
 * @param asyncRoute 完整的异步路由表（前端定义：系统有哪些能力）
 * @param routes     后端给的「该用户可访问的路由名」数组，如 ['User','Role','Product',...]
 *                   注意：后端返回的路由名可能是大写（如 'User'），前端定义的 name 是小写（'user'），
 *                   所以匹配前统一转 toLowerCase，避免大小写不一致导致菜单被全过滤掉。
 *
 * 规则：父路由只要有存活子项就保留；叶子路由 name（忽略大小写）在列表里才保留。
 */
export function filterAsyncRoute(asyncRoute: RouteRecordRaw[], routes: string[]): RouteRecordRaw[] {
  // 统一转小写，后续匹配都按小写比，规避「后端大写 / 前端小写」对不上的问题
  const routeNames = routes.map((r) => r.toLowerCase())
  // 结果数组：装「当前用户能看」的路由
  const result: RouteRecordRaw[] = []
  // 遍历传进来的每一条路由
  for (const item of asyncRoute) {
    if (item.children && item.children.length > 0) {
      // 情况A：是父路由（容器）→ 先把儿子们拿去递归筛一遍
      const filteredChildren = filterAsyncRoute(item.children, routes)
      // 父路由靠子项存活：儿子筛完还剩几个？
      if (filteredChildren.length > 0) {
        // 还有活着的儿子 → 造一个「复制版父路由」，把它的 children 换成筛剩下的，推入结果
        //   { ...item }           = 复制父路由自身属性（path/component/meta），不污染原 asyncRoutes
        //   children: filteredChildren = 只带活下来的儿子（被删的儿子不跟着回来）
        result.push({ ...item, children: filteredChildren })
      }
      // 儿子全被删光 → 什么都不 push，父路由整体不保留
    } else if (routeNames.includes((item.name as string).toLowerCase())) {
      // 情况B：是叶子路由（没儿子）→ 名字（忽略大小写）在后端列表里才保留，否则跳过
      result.push(item)
    }
  }
  return result
}
```

> **匹配忽略大小写的原因**：真实后端返回的 `routes` 常是首字母大写（`['User','Role',...]`），而前端 `name` 是小写（`'user'`）。`Array.includes` 严格区分大小写，直接比会对不上、把异步路由全过滤掉。代码里统一 `toLowerCase()` 后比较，前端不再依赖后端命名风格。该函数在 `getUserInfo` 里调用（步骤 3），即登录后首次进保护页或刷新时执行一次。

## 步骤 3：扩展 `src/store/modules/user.ts`

这是核心。要加：token（持久化）、userInfo、menuRoutes、三个 action。

```ts
// src/api/user/type.ts —— 给 userinfoType 加 export
export interface userinfoType {
  avatar: string
  buttons: string[]
  name: string
  roles: string[]
  routes: string[]
}
// 真后端：data 直接是用户对象
export interface userResponseData {
  code: number
  data: userinfoType
}
```

> **为什么 token 要存 localStorage？**
> pinia 状态在**整页刷新时会重置**。如果不持久化，刷新后 `userStore.token` 变空，守卫会当成「未登录」把用户踢回登录页，权限就丢了。所以 token 同时存 pinia（运行时用）和 localStorage（刷新后恢复）。`getUserInfo` 同理需要在守卫里重新拉一次。
>
> **为什么 `userInfo.name` 能当「是否已加载」的标志？**
> 只有 `getUserInfo` 成功才会给 `userInfo` 赋值。守卫里判断 `userStore.userInfo.name` 有值 = 用户信息已加载过 = 动态路由已挂载，直接放行；否则先拉信息再放行。

```ts
import { ref } from 'vue'
import { defineStore } from 'pinia'
import { constantRoutes, asyncRoutes, anyRoute } from '@/router/routes'
import { loginAPI, userinfoAPI } from '@/api/user'
import type { loginForm, userinfoType } from '@/api/user/type'
import { filterAsyncRoute } from '@/utils/routeFilter'
import router from '@/router'

// 从 localStorage 读已存的 token（刷新页面时不丢登录态）
const getToken = () => localStorage.getItem('TOKEN') || ''

const useUserStore = defineStore('user', () => {
  const token = ref(getToken())
  // 2. 用户信息（含 roles / buttons / routes）
  //    Partial 不能省：初始是空 {}，但后面要读 .name / .routes，
  //    用 Partial<userinfoType> 让 TS 知道「这是 userinfoType，只是字段可能还没填」
  const userInfo = ref<Partial<userinfoType>>({})
  const menuRoutes = ref(constantRoutes)

  // 登录：拿 token，存 pinia + localStorage
  const userLogin = async (data: loginForm) => {
    const res = await loginAPI(data)
    if (res.code === 200) {
      token.value = res.data.token
      localStorage.setItem('TOKEN', res.data.token)
      return 'ok'
    } else {
      return Promise.reject(new Error(res.data.message || '登录失败'))
    }
  }

  // 获取用户信息：拉取 data（真后端直接返回用户对象），算菜单，动态 addRoute
  const getUserInfo = async () => {
    const res = await userinfoAPI()
    if (res.code === 200) {
      userInfo.value = res.data
      // 过滤出当前用户能看的异步路由（父路由靠子项存活，无需 name）
      // routes 理论上一定有值，用 ?? [] 兜底让类型收窄、避免 undefined
      const userAsyncRoutes = filterAsyncRoute(asyncRoutes, userInfo.value.routes ?? [])
      // 菜单 = 常量路由 + 过滤后的异步路由（菜单组件读的就是 menuRoutes）
      menuRoutes.value = [...constantRoutes, ...userAsyncRoutes]
      // 动态挂载：每个异步路由 addRoute，最后补 anyRoute 兜底
      userAsyncRoutes.forEach((route) => {
        router.addRoute(route)
      })
      router.addRoute(anyRoute)
      return 'ok'
    } else {
      return Promise.reject(new Error(res.data.message || '获取用户信息失败'))
    }
  }

  // 退出登录：清 token + 清用户信息
  const logout = async () => {
    token.value = ''
    userInfo.value = {}
    localStorage.removeItem('TOKEN')
    // 动态添加的路由在整页刷新时会清空，无需手动 removeRoute；
    // 若后续做 SPA 内不刷新退出，需要遍历 removeRoute。
    return 'ok'
  }

  return { token, userInfo, menuRoutes, userLogin, getUserInfo, logout }
})

export default useUserStore
```

> **类型说明**：`userInfo` 用 `Partial<userinfoType>`——这是唯一不能省的注解（未登录时为空 `{}`，`Partial` 让 TS 既允许空对象又能访问 `.name`/`.routes`）。`token`、`menuRoutes` 靠 `ref` 自动推断，无需手写泛型；因 `routes.ts` 已标好类型，这里无 `as` 断言。

## 步骤 4：给 `src/router/index.ts` 加守卫

> **`router.beforeEach` 是什么？**
> 它是 vue-router 的**全局前置守卫**：每次路由「即将跳转、但还没真正跳」时先调用，可拦截导航、决定放行/改道。参数：`to`（目标）、`from`（来源）、`next`（必须调用的回调，每个分支只能调一次，不调导航会卡住）。`async` 是因为里面要 `await getUserInfo()`。
>
> 文档用到的关键 `next` 用法：
>
> | 写法                                                     | 含义                                                            |
> | -------------------------------------------------------- | --------------------------------------------------------------- |
> | `next({ path: '/login', query: { redirect: to.path } })` | 改道到登录页，并带 `redirect` 参数（登录完跳回原页）            |
> | `next({ ...to, replace: true })`                         | 用新路由表重新解析一次 `to`（动态路由刚挂上时用，避免白屏/404） |
>
> **为什么用 `next({ ...to, replace: true })` 而非直接 `next()`？** `getUserInfo` 里刚 `addRoute` 挂上动态路由，直接 `next()` 用的是挂载前的路由表，目标页还不存在 → 白屏/404；`replace: true` 会中断当前导航、用新路由表重新匹配一次，动态路由已存在才能正确进入。

```ts
import { createRouter, createWebHashHistory } from 'vue-router'
import { constantRoutes } from '@/router/routes'
import useUserStore from '@/store/modules/user'

const router = createRouter({
  history: createWebHashHistory(),
  routes: constantRoutes,
  scrollBehavior() {
    return { left: 0, top: 0 }
  },
})

// 白名单：不需要 token 也能进的页面
const whiteList = ['/login']

router.beforeEach(async (to, from, next) => {
  const userStore = useUserStore()
  const token = userStore.token || localStorage.getItem('TOKEN')

  if (token) {
    // 已登录
    if (to.path === '/login') {
      // 已经登录还想去登录页？直接回首页
      next('/')
    } else {
      // 已登录去其他页：确保用户信息已加载（动态路由依赖它）
      if (userStore.userInfo.name) {
        next()
      } else {
        try {
          await userStore.getUserInfo()
          // 动态路由刚挂上，重新解析一次目标路由
          next({ ...to, replace: true })
        } catch (error) {
          await userStore.logout()
          next({ path: '/login', query: { redirect: to.path } })
        }
      }
    }
  } else {
    // 未登录
    if (whiteList.includes(to.path)) {
      next()
    } else {
      // 带上 redirect，登录完跳回原页面
      next({ path: '/login', query: { redirect: to.path } })
    }
  }
})

export default router
```

## 步骤 5：`src/utils/request.ts` 注入 token

当前请求拦截器是空实现，后端 `/api/v1/acl/user/info` 靠请求头 `token` 识别用户，所以必须注入。

> **为什么从 localStorage 读，而不是 import userStore？**
> `request.ts` 被 `api/user` 引用，`api/user` 又被 `userStore` 引用。若 `request.ts` 再 import `userStore` 会形成**循环依赖**。从 `localStorage` 直接读 token 简单且避开了这个问题（token 本来就在 localStorage 里）。

把请求拦截器改成：

```ts
//请求拦截器
request.interceptors.request.use((config) => {
  // 从 localStorage 读 token（避免直接 import userStore 造成循环依赖）
  const token = localStorage.getItem('TOKEN')
  if (token) {
    config.headers.token = token
  }
  return config
})
```

## 步骤 6：最小可用登录页 `src/views/login/index.vue`

用 Element Plus 的 `el-form`（组件已被 `unplugin-vue-components` 自动引入，直接用；`ElMessage` 也自动引入）。

```vue
<template>
  <div class="login_container">
    <el-form ref="loginFormRef" :model="loginForm" :rules="rules" class="login_form">
      <h2 class="title">Vue Admin 登录</h2>
      <el-form-item prop="username">
        <el-input
          v-model="loginForm.username"
          placeholder="用户名（admin / user）"
          :prefix-icon="User"
        />
      </el-form-item>
      <el-form-item prop="password">
        <el-input
          v-model="loginForm.password"
          type="password"
          show-password
          placeholder="密码（111111）"
          :prefix-icon="Lock"
        />
      </el-form-item>
      <el-form-item>
        <el-button type="primary" class="login_btn" :loading="loading" @click="handleLogin">
          登录
        </el-button>
      </el-form-item>
    </el-form>
  </div>
</template>

<script setup lang="ts">
import { ref, reactive } from 'vue'
import { useRoute, useRouter } from 'vue-router'
import { User, Lock } from '@element-plus/icons-vue'
import type { FormInstance, FormRules } from 'element-plus'
import useUserStore from '@/store/modules/user'

const $router = useRouter()
const $route = useRoute()
const userStore = useUserStore()

const loginFormRef = ref<FormInstance>()
const loading = ref(false)
const loginForm = reactive({
  username: 'admin',
  password: '111111',
})

// 表单校验规则
const rules = reactive<FormRules>({
  username: [{ required: true, message: '请输入用户名', trigger: 'blur' }],
  password: [{ required: true, message: '请输入密码', trigger: 'blur' }],
})

const handleLogin = async () => {
  // 先校验表单
  await loginFormRef.value?.validate()
  loading.value = true
  try {
    await userStore.userLogin(loginForm)
    // 跳回登录前想去的页面，没有就回首页
    const redirect = ($route.query.redirect as string) || '/'
    $router.push(redirect)
  } catch (error) {
    // 登录失败提示（userLogin 里 reject 的 message）
    // error 默认是 unknown，用 instanceof 收窄后再取 message
    ElMessage.error(error instanceof Error ? error.message : '登录失败')
  } finally {
    loading.value = false
  }
}
</script>
```

## 步骤 7：让后端返回用户的 `routes`（权限数据从哪来）

`routes` 这个「能看哪些菜单」的数组，来源有两种，按你实际情况选一种。**前端 `filterAsyncRoute` / 守卫 / store 的代码在两种情况下完全一样，都不用动。**

### 情况 A：你有真实后端（当前情况）

本仓库**没有**前端 mock（无 MSW），直接对接 `apps/server` 真实后端即可。只要保证后端两个接口返回前端期望的结构：

- `POST /api/v1/acl/index/login` → `{ code: 200, data: { token: 'xxx' } }`
- `GET /api/v1/acl/user/info`（具体路径以 `USERINFO_URL` 常量为准）→ `{ code: 200, data: { avatar, name, roles, buttons, routes } }`（真后端 `data` 直接是用户对象，无 `checkUser` 包裹）

其中 `data.routes` 是**后端按当前登录用户从数据库查出的「能看的路由名数组」**：管理员返回全部叶子名，普通用户只返回商品管理相关叶子名。前端拿它过滤，自然就看到不同的菜单。

> **本仓库无 MSW**：`src/main.ts` 不会启动 mock worker，无需关闭任何 mock。若此前拷贝了含 `mocks/browser` 的 `main.ts`，直接删掉 mock 相关导入即可。`.env.development` 的 `VITE_API_BASE_URL` 设为 `http://localhost:9000`（后端端口）。

### 情况 B：没有后端，用 MSW mock（学习 / 演示用）

把 `src/mocks/handlers.ts` 的 `createUserList()` 改成下面这样，定义两个用户：**管理员（admin）** 和 **普通用户（user）**。

> **`roles` / `buttons` / `routes` 三者职责（为什么权限由 `routes` 决定）**
>
> - `routes` 是**真正驱动菜单**的字段：里面列了哪些路由名，用户就能看到哪些菜单。
> - `roles`（`['管理员']` / `['普通用户']`）只是「身份标签」，目前纯展示用，不参与过滤。
> - `buttons` 留给以后「按钮级权限」用（比如某些按钮只有特定角色能看到），本步骤没做。
>
> 因为用了步骤 2 的「父路由靠子项存活」逻辑，这里 `routes` **不需要写 `'acl'` / `'product'`**，只列叶子路由名即可。管理员给全部叶子，普通用户只给商品管理相关叶子，自然就看不到「权限管理」菜单。

把 `createUserList()` 改成：

```ts
function createUserList(): AccountUser[] {

      roles: ['普通用户'], // 身份标签
      buttons: ['cuser.detail'],
```

## 常见坑（执行时遇到对照）

- **动态页面白屏 / 404**：忘了 `next({ ...to, replace: true })`，或 `anyRoute` 没在最后 `addRoute`。
- **刷新后菜单没了**：守卫里没判断「未加载 userInfo 就先 `getUserInfo`」，或 `getUserInfo` 没 `addRoute`。
- **info 接口返回 201 获取失败**：请求拦截器没注入 token，或 mock 里 `token` 不匹配（确认 `localStorage` 的 key 是 `TOKEN`）。
- **菜单父级不显示**：子路由 `name` 没写进 mock 的 `routes`（父路由本身不用写，靠子项存活）。
- **登录后菜单只剩首页和数据大屏**：后端返回的 `routes` 路由名是大写（如 `User`），前端 `name` 是小写（`user`），`Array.includes` 严格区分大小写导致全部异步路由被过滤。需把 `filterAsyncRoute` 改成 `toLowerCase()` 后比较（见步骤 2）。
- **`ElMessage` 报未定义**：本项目用 `unplugin` 自动导入，直接在 `<script setup>` 里用即可，不要手动 `import`。

## 设计要点速查（为什么这么写）

| 设计点                               | 为什么                                                                              |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| 路由拆 constant / async / anyRoute   | 权限页面不能一开始就注册，否则未登录也能直访；anyRoute 必须最后挂                   |
| 父路由不给 `name`                    | 过滤逻辑是「父路由靠子项存活」，父路由不参与名字匹配                                |
| 叶子用 `name` 匹配而非 `path`        | `path` 混相对/绝对易错，`name` 唯一稳定                                             |
| 匹配忽略大小写（`toLowerCase`）      | 后端返回路由名首字母大写（如 `User`），前端 `name` 小写（`user`），不忽略会全被过滤 |
| token 存 localStorage                | 刷新页面 pinia 重置，需从 localStorage 恢复登录态                                   |
| 守卫里 `next({...to, replace:true})` | 动态路由刚 addRoute，需重新匹配一次目标                                             |
| 请求拦截器从 localStorage 读 token   | 避免 import userStore 造成循环依赖                                                  |
| `routes` 驱动菜单，`roles` 只是标签  | 真正决定权限的是后端返回的 `routes` 数组                                            |
