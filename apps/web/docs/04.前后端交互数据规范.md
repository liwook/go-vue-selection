# 04. 前后端交互数据规范

---

## 一、前后端交互字段类型

> **ID 用字符串**：本仓库 `swagger.json` 中所有 ID 字段（如 `skuId`、`spuId`、`tmId`、`menuId`、`attrId`、`parentId`）均为 `string` 类型，前端 TS 对应 `string`，避免 JS `Number` 精度丢失。

### 1.1 契约铁律

1. **前后端统一 camelCase**：JSON 字段与前端 TS 同名（如 `priceCent`、`weightMg`、`skuId`），不做 snake_case ↔ camelCase 映射。
2. **最小整数单位契约**：金额 `priceCent`（分）、重量 `weightMg`（毫克）等以最小整数对外返回（见 swagger 字段 description「单位：分/毫克，JSON number 类型」）；**API 层是唯一转换边界**，提交转一次、返回转一次，其余透明。
3. **字段名自带单位后缀**：`priceCent`、`weightMg` 等拒绝魔法数字与隐式契约。
4. **时间只用 RFC3339**：`createTime`/`updateTime` 为 `string` 类型（RFC3339 格式）。
5. **ID 用字符串**：所有 `xxxId`（如 `skuId`、`spuId`、`tmId`、`category3Id`）在 swagger 中为 `string`，前端用 `string`。
6. **类型不手写**：前端接口类型由后端 `swagger.json` 经 `pnpm api:gen` 自动生成（见第三章），产物 `src/api/schema.d.ts`，请求走 `src/api/client.ts`。

### 1.2 字段类型映射表（取自真实 swagger）

| 业务含义   | 前端 TS / 后端 JSON (camelCase) | swagger 类型 | 说明                                              |
| :--------- | :------------------------------ | :----------- | :------------------------------------------------ |
| **ID**     | `skuId` / `spuId` / `tmId`      | `string`     | 所有 ID 均为字符串，避免 JS 精度丢失             |
| **金额**   | `priceCent`                     | `integer`    | 单位：分（最小货币单位），description 明确标注    |
| **重量**   | `weightMg`                      | `integer`    | 单位：毫克（最小重量单位）                        |
| **时间**   | `createTime` / `updateTime`     | `string`     | RFC3339 格式                                      |
| **名称**   | `skuName` / `spuName`           | `string`     | 业务名称                                          |
| **状态**   | `isSale`                        | `integer`    | 离散值（0/1），非计量单位                         |
| **布尔值** | `select` / `status`             | `boolean`    | 禁用 1/0                                          |

### 1.3 单位转换边界（前端）

- **API 层是唯一转换边界**：表单内用业务单位（`priceYuan`、`weightGram`），提交时转一次最小整数单位（`yuanToCent(form.priceYuan)`），返回时转回业务单位展示（`centToYuan(item.priceCent)`）。
- **store 永远存最小单位整数**：不要提前把 `centToYuan(...)` 结果写回 store（会变 `string`，丢精度且无法精确编辑）。
- **转换函数落地**：需要时按映射表在 `utils/unit.ts` 实现 `yuanToCent`/`centToYuan`/`gramToMg`/`mgToGram` 等，务必用 `Math.round` 规避浮点误差（具体实现以工程内实际文件为准）。

### 1.4 表单提交示例（Vue3）

```vue
<template>
  <el-form-item label="售价 (元)">
    <el-input v-model.number="form.priceYuan" type="number" :step="0.01" />
  </el-form-item>
  <p>售价: {{ centToYuan(product.priceCent) }} 元</p>
</template>

<script setup lang="ts">
import { reactive } from 'vue'
import { client } from '@/api/client'
import { yuanToCent, centToYuan, gramToMg } from '@/utils/unit'
import type { paths } from '@/api/schema' // 类型由 api:gen 生成，见第三章

const form = reactive({ priceYuan: 8999.0, weightGram: 187 })
const product = reactive({ priceCent: 0, weightMg: 0 })

const handleSubmit = async () => {
  const { data, error } = await client.POST('/api/v1/product', {
    body: {
      skuId: 'SKU_001',
      name: 'iPhone 15 Pro',
      priceCent: yuanToCent(form.priceYuan), // 8999 元 → 899900 分
      weightMg: gramToMg(form.weightGram),   // 187 克 → 187000 毫克
    },
  })
  if (error) return
  Object.assign(product, data?.data) // data.data 字段已是 camelCase
}
</script>
```

## 二、通用响应结构与接口示例

### 2.1 统一响应结构

所有接口返回 `{ code, data, message }`：

- **成功**：`code === 200`，数据在 `data`（分页接口 `data` 含 `records` / `total`，不再包顶层 `meta`）。
- **业务错误**：走 **HTTP 200 + body.code≠200**，由响应体 `code` 区分（如 `110002` 未登录、`110003` token 失效、`110005` 无权限、`110001+` 各业务校验错误），前端统一提示 `message`。
- **基础设施异常**：走真实 HTTP 状态码（如 500），由 client 按 HTTP 拦截（见 3.4）。所有 handler 已在 swagger 标注 `@Failure 500`。
- **全局 404 兜底**：访问未注册路由由 `NoRoute` 统一返回 **HTTP 404 + `code 110004`（CodeNoRoute）**，属框架级行为，与具体 handler 无关。

### 2.2 错误码 → HTTP 状态对照表

| code    | HTTP  | 说明                          |
| :------ | :---- | :---------------------------- |
| `200`   | 200   | 成功                          |
| `11xxxx`| 200   | 业务错误（含 110002/03/05 等）|
| `110004`| **404**| 路由未匹配（NoRoute 兜底）   |
| `99xxxx`| **500**| 系统错误（panic / DB / 外部） |

### 2.3 示例：获取 SKU 详情 `GET /api/v1/product/sku/{skuId}`

**Response:**

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "skuId": "123", "spuId": "456", "tmId": "789", "category3Id": "101",
    "skuName": "iPhone 15 Pro",
    "priceCent": 899900, "weightMg": 187000, "isSale": 1,
    "createTime": "2026-01-15T10:30:00Z", "updateTime": "2026-01-15T10:30:00Z"
  }
}
```

> 约定：ID 均为字符串；计量值已是最小整数单位（`priceCent` 为分，`weightMg` 为毫克）；时间字段为 RFC3339 字符串；字段名 camelCase，与 swagger / 前端 TS 一致。

## 三、用 openapi-typescript + openapi-fetch 生成类型安全 API

后端用 `swag`（`gin-swagger`）生成的是 **Swagger / OpenAPI 2.0** 文档（`apps/server/api/swagger.json`）。前端 `openapi-typescript@7` 仅支持 OpenAPI 3.0+，因此本仓库采用「消费侧适配」方案：

> **方案 A（不动后端）**：在生成类型这一步把 2.0 转成 3.0，再交给 `openapi-typescript` 产出 `schema.d.ts`。
> 后端 `swag` 的 OpenAPI 3.0 输出目前仍是 beta，不在生产后端引入风险；前端只消费已生成的 `swagger.json`，隔离后端不稳定性。

### 3.1 依赖

- `swagger2openapi`（devDependency）：把 2.0 转 3.0
- `openapi-typescript`（devDependency）：由 3.0 生成 TS 类型
- `openapi-fetch`（runtime 依赖）：类型安全的请求 client

### 3.2 生成脚本（`apps/web/package.json`）

```json
{
  "scripts": {
    "api:gen": "swagger2openapi ../server/api/swagger.json -o src/api/openapi.json && openapi-typescript src/api/openapi.json -o src/api/schema.d.ts"
  }
}
```

两步含义：

1. `swagger2openapi` 读取后端 `swagger.json`（2.0），输出中间文件 `src/api/openapi.json`（3.0）。
2. `openapi-typescript` 读取 3.0 文件，生成 `src/api/schema.d.ts`（`paths` / `components["schemas"]` 等类型）。

### 3.3 产物提交策略（clone 即 `pnpm dev`）

- ✅ `src/api/schema.d.ts` **提交进仓库**：他人 clone 后类型文件已在，无需额外步骤即可运行。
- ❌ `src/api/openapi.json`（转换中间物）**gitignore**：仅生成过程临时文件，不参与运行。
- `apps/web/biome.json` 用 `files.includes` 否定模式忽略 `src/api/schema.d.ts`，避免 `api:gen` 重跑时被格式化工具重排产生无意义 diff。

### 3.4 类型安全 Client（`src/api/client.ts`）

基于 `openapi-fetch`，baseURL 用 `/api`（与 vite 代理一致），并在 `onResponse` 钩子里统一拦截两类失败（见 2.1）：业务错误（HTTP 200 + body.code≠200）与基础设施异常（HTTP 非 2xx，如 500）：

```typescript
import { ElMessage } from 'element-plus'
import createClient from 'openapi-fetch'
import { useUserStore } from '@/store/modules/user'
import type { paths } from './schema'
import 'element-plus/es/components/message/style/css'

// 鉴权类业务码：需要登录 / 无效 Token（与后端 pkg/result/code.go 保持一致）
const AUTH_ERROR_CODES = [110002, 110003]

// 跳转到登录页（避免在拦截器里直接依赖 router，用 location 兜底；hash 模式无需刷新）
function redirectToLogin() {
  if (location.hash !== '#/login' && location.pathname !== '/login') {
    location.hash = '#/login'
  }
}

// 当前是否在登录页（或正在跳往登录页）—— 用于鉴权类错误时抑制重复弹窗
function isAtLogin() {
  return location.hash.startsWith('#/login') || location.pathname === '/login'
}

export const client = createClient<paths>({
  baseUrl: '/api',
})

client.use({
  onResponse: async ({ response }) => {
    // 基础设施异常：未捕获 panic / 中间件错误 / 网关 5xx 等，直接返回非 2xx
    if (response.status < 200 || response.status >= 300) {
      ElMessage({ type: 'error', message: `服务异常 (${response.status})` })
      throw new Error(`HTTP ${response.status}`)
    }
    const ct = response.headers.get('content-type') ?? ''
    if (!ct.includes('application/json')) return
    const data = (await response.clone().json()) as { code?: number; message?: string }
    // 业务错误：HTTP 200 但 body.code !== 200
    if (typeof data.code === 'number' && data.code !== 200) {
      if (AUTH_ERROR_CODES.includes(data.code)) {
        // 鉴权类错误：全局兜底——清登录态 + 跳登录页
        useUserStore().clearAuth()
        const wasAtLogin = isAtLogin()
        redirectToLogin()
        // 仅当用户「在业务页主动操作」触发失效时才提示一次；
        // 若是「跳往/已处于登录页」则静默，避免「打开登录页就弹窗」的糟糕体验。
        if (!wasAtLogin) {
          ElMessage({ type: 'warning', message: '登录已过期，请重新登录' })
        }
      } else {
        ElMessage({ type: 'error', message: data.message ?? '请求失败' })
      }
      throw new Error(data.message ?? '请求失败')
    }
  },
})
```

### 3.5 调用示例（类型推导，写错字段名 / 类型编译报错）

`client` 的 `GET` / `POST` / `PUT` / `DELETE` 等方法，其 `body`、`query`、`params` 以及返回 `data` 的类型全部由 `schema.d.ts` 推导：

```typescript
import { client } from '@/api/client'

// 登录：body 类型、返回类型均由 schema.d.ts 推导
const { data, error } = await client.POST('/api/v1/acl/index/login', {
  body: { username: 'admin', password: '123456' },
})
if (error) return
// data.data 类型即 login 响应的 data（string token）

// 获取 SKU 详情：path 参数 skuId 为 string，返回 data.data 已是 ResponseSkuInfo 视图类型
const { data: sku, error: e2 } = await client.GET('/api/v1/product/sku/{skuId}', {
  params: { path: { skuId: '123' } },
})
if (e2) return
// 字段名/类型全部由 schema.d.ts 推导，写错会编译报错
console.log(sku?.data.skuId)     // string
console.log(sku?.data.priceCent) // number（分）
console.log(sku?.data.weightMg)  // number（毫克）
```

> 旧代码仍可继续用 `src/utils/request.ts`（axios）。新增接口优先用 `client`，二者 baseURL 与错误处理语义一致。

### 3.6 何时需要重跑

- 仅当后端接口变动、`apps/server` 重新生成 `swagger.json` 后，再到 `apps/web` 执行：

  ```bash
  # 后端：在 apps/server 下重新生成 swagger 文档
  # make swagger 是下方命令的封装，等价
  swag init -g main.go -o api --parseDependency --parseInternal

  # 前端：消费 swagger.json 生成类型（apps/web）
  pnpm api:gen
  ```

- 日常 clone / `pnpm dev` 不需要此步骤（类型文件已提交）。
- 本次已重跑：所有 handler 补 `@Failure 500` 后执行 `swag init`，并 `pnpm api:gen` 同步更新了 `src/api/schema.d.ts`（已提交）。
