# 05. 路由守卫与动态权限路由实现

> 在「静态路由表 + Layout + 递归菜单」骨架上接**鉴权路由**：未登录访问任意页跳 `/login`；登录后按用户 `routes` 动态挂菜单（管理员看全部，普通用户只看商品管理）；刷新权限不丢。

---

## 步骤 0：核心流程与原理（必读，避免改错）

```bash
登录页填账号密码
  └─> userStore.userLogin(form)  ──> POST /api/v1/acl/index/login 拿到 data（token 字符串）
        └─> token 存 pinia + localStorage('token')
        └─> 跳转 redirect || '/home'

路由守卫 beforeEach
  └─> 有 token？
       ├─ 无 token 且不是 /login  ──> 跳 /login?redirect=当前路径
       ├─ 有 token 且去 /login   ──> 重定向到 /
       └─ 有 token 且去其他页：
             ├─ 动态路由已挂载（isRoutesAdded 为 true）→ 直接放行
             └─ 未挂载 ──> await userStore.getUserInfo()
                   ├─ 成功：filterAsyncRoute 算出菜单 + router.addRoute 动态挂载
                   │         ├─ isRoutesAdded = true
                   │         └─> return { ...to, replace: true }  // 关键：重新解析一次
                   └─ 失败：logout 清 token/menuRoutes，跳 /login
```

**关键点**：动态路由必须在「拿到用户信息之后」用 `router.addRoute` 挂上去，挂完要 `return { ...to, replace: true }` 让路由重新匹配一次，否则首次进动态页面会是白屏/404。同一个 session 内用 `isRoutesAdded` 标记只挂载一次，避免每次导航都重复 `addRoute` + 重新解析导致死循环。

> **⚠️ 落地前须知（本仓库现状）**
>
> 1. **接口走 openapi 客户端**：`src/api/client.ts` 封装 `createClient<paths>`（`baseUrl: '/api'`），类型来自 `src/api/schema.d.ts`。登录入口是 `src/api/index.ts` 的 `login()`。
> 2. **token 用 `Authorization: Bearer <token>` 头**：后端 JWT 中间件只读这个头，本仓库只在 `client`（`openapi-fetch`）里注入，写自定义 `token` 头无效。

## 步骤 1：拆分 `src/router/routes.ts`

把现在的「全部静态」拆成三块。

> **为什么拆三块？**
>
> - `constantRoutes`：不需要权限的页面（登录、首页、大屏、404 页）。任何人都能进，一开始就注册进 router。
> - `asyncRoutes`：需要权限的页面（权限管理、商品管理）。**不能一开始就注册**，否则没登录也能直接访问。登录后按用户权限用 `router.addRoute` 挂上。
> - `anyRoute`：404 兜底通配。**必须放最后 addRoute**。如果它留在 `constantRoutes` 里，会在动态路由之前把所有未知路径直接重定向到 /404，导致动态页面进不去。
>   **为什么父路由（/acl、/product）这里不给 `name`？**
>   因为本方案的过滤逻辑是「父路由只要还有存活的子项就保留」（见步骤 2），父路由本身不参与名字匹配，所以不需要 `name`。子路由的 `name`（`user`/`role`/...）才是过滤的依据，必须保留。
>   （对比另一种写法：让父路由也出现在后端 `routes` 列表里，那父路由就得有 `name`。本方案更干净——父路由纯粹是个容器，不该为了「被保留」而硬塞进权限列表。）

## 步骤 2：新增 `src/utils/routeFilter.ts`

> **为什么需要这个函数？**
> `asyncRoutes` 定义的是「系统总共能有哪些页面」，但不同用户该看的不同。这函数就是那把「剪刀」：拿后端返回的「能看名单」(`routes`) 去路由表里剪掉对不上的枝叶，产出「当前用户专属的路由树」，同时喂给 `menuRoutes`（菜单显示）和 `router.addRoute`（路由挂载）。前端定义「有哪些能力」，后端决定「谁有哪个」——函数连接两头。
>
> 过滤规则：父路由（`/acl`、`/product`）是容器，有存活子项才保留（故父路由无需 `name`）；叶子路由看 `name` 是否在后端列表里（用 `name` 而非 `path`，因 `path` 混相对/绝对易错）。

```ts
import type { RouteRecordRaw } from 'vue-router'

/**
 * 根据后端返回的 routes（路由名数组）过滤异步路由
 * @param asyncRoute 完整的异步路由表（前端定义：系统有哪些能力）
 * @param routes     后端给的「该用户可访问的路由名」数组
 *                   注意：后端返回的路由名可能是大写（如 'User'），前端定义的 name 是小写（'user'），
 *                   所以匹配前统一转 toLowerCase，避免大小写不一致导致菜单被全过滤掉。
 */
export function filterAsyncRoute(asyncRoute: RouteRecordRaw[], routes: string[]): RouteRecordRaw[] {
  // 统一转小写一次，规避「后端大写 / 前端小写」对不上的问题
  const routeNames = routes.map((item: string) => item.toLowerCase())
  // 用 reduce 收集，不修改入参原数组（多次调用不会互相污染）
  return asyncRoute.reduce((acc: RouteRecordRaw[], item: any) => {
    if (!item.children) {
      // 叶子路由：name（已统一小写）在后端列表里才保留
      if (routeNames.includes(item.name as string)) {
        acc.push(item)
      }
    } else {
      // 父路由：先递归筛儿子，有存活子项才保留（复制父路由并替换 children，不污染原表）
      const filteredChildren = filterAsyncRoute(item.children, routes)
      if (filteredChildren.length > 0) {
        acc.push({ ...item, children: filteredChildren } as RouteRecordRaw)
      }
    }
    return acc
  }, [])
}
```

## 步骤 3：新增 `src/store/modules/user.ts`

### 3.1 先装 pinia（为什么需要它）

**为什么要用 pinia？** token 和用户信息需要在「路由守卫」「登录页」「菜单组件」之间共享：守卫要判断有没有登录、菜单要根据 `routes` 渲染。这些组件没直接的父子传值关系，用组件 props 传不现实，所以放进一个全局 store。这里用 pinia 来存 `token / 用户信息(name/avatar/buttons) / menuRoutes`。

当前仓库没装 pinia，先安装并在 `main.ts` 中注册（**顺序在 router 之前**）：

```bash
# 在 apps/web 目录下
pnpm add pinia
```

```ts
// src/main.ts：pinia 必须在 router 之前注册，
// 否则路由守卫里 useUserStore() 拿不到已激活的 pinia 实例
import { createPinia } from 'pinia'
// ...
// 注册 pinia
app.use(createPinia())
// 注册路由
app.use(router)
app.mount('#app')
```

### 3.2 写 userStore

store 直接调 openapi 客户端 `client`（`src/api/client.ts`），**类型从 `src/api/schema.d.ts` 自动派生，不手写 interface、也不新增 `api/user.ts`**：

> 这里用 **Setup Store** 写法（Pinia 官方推荐、与 Vue 3 Composition API 风格一致）：`state` 用 `ref()` 声明、`actions` 是普通函数、错误直接 `throw` 由调用方 `await` 捕获，不再包 `try/catch + Promise.reject`。

```ts
import { defineStore } from 'pinia'
import { ref } from 'vue'
import { client } from '@/api/client'
import type { paths } from '@/api/schema'
import type { components } from '@/api/schema'

// 登录入参类型（对应 openapi 里的 POST /api/v1/acl/index/login）
type LoginFormData =
  paths['/api/v1/acl/index/login']['post']['requestBody']['content']['application/json']

// 用户信息结构（对应 GET /api/v1/acl/user/info 的 data 字段）
type ResponseUserInfo = components['schemas']['types.ResponseUserInfo']

export const useUserStore = defineStore('User', () => {
  // state
  const token = ref(localStorage.getItem('token') || '')
  // 原始 routes（menu.code 数组），守卫据此 filterAsyncRoute；layout 菜单见步骤说明
  const menuRoutes = ref<string[]>([])
  const name = ref('') // 用户名（对应后端 data.name）
  const avatar = ref('')
  const buttons = ref<string[]>([]) // 按钮权限
  const isRoutesAdded = ref(false)  // 动态路由是否已挂载（防止每次导航重复 addRoute）

  // 重置权限态：登录成功 / 退出时调用，确保用新账号重新拉取并挂载动态路由
  function resetUserState() {
    token.value = ''
    name.value = ''
    avatar.value = ''
    buttons.value = []
    menuRoutes.value = []
    isRoutesAdded.value = false
  }

  // 登录：拿到 token 后存本地（持久化），后续靠 token 换用户信息
  // client 失败（网络/HTTP/业务码非200）直接 throw，调用方 await 时自然捕获
  async function userLogin(data: LoginFormData) {
    const { data: res } = await client.POST('/api/v1/acl/index/login', { body: data })
    if (res?.code !== 200) throw new Error(res?.message || '登录失败')
    const newToken = res.data as string
    resetUserState()
    token.value = newToken
    localStorage.setItem('token', newToken)
  }

  // 拿用户信息：靠 token 换 routes/buttons/name/avatar（menuRoutes 存原始 routes）
  async function getUserInfo() {
    const { data: res } = await client.GET('/api/v1/acl/user/info')
    if (res?.code !== 200) throw new Error(res?.message || '获取用户信息失败')
    const data = res.data as ResponseUserInfo | undefined
    if (data) {
      name.value = data.name ?? ''
      avatar.value = data.avatar ?? ''
      buttons.value = data.buttons ?? []
      menuRoutes.value = data.routes ?? []
    }
  }

  // 清除登录态：清 token + 清本地存储，退出登录 / token 失效统一走这里（单一数据源）
  function clearAuth() {
    resetUserState()
    localStorage.removeItem('token')
  }

  // 退出登录：调后端登出接口 → 清 token/用户信息
  async function userLogout() {
    const { data: res } = await client.POST('/api/v1/acl/index/logout')
    if (res?.code !== 200) throw new Error(res?.message || '退出失败')
    clearAuth()
  }

  return { token, menuRoutes, name, avatar, buttons, isRoutesAdded, userLogin, getUserInfo, userLogout, clearAuth }
})
```

> **权限数据从哪来（routes 来源）**
> 本仓库直接对接 `apps/server` 真实后端。`res.data.routes` 是后端按当前用户从 `menu` 表查出的「可看路由名数组」：管理员返回全部 `menu.code`，普通用户只返回其角色关联的少量 `code`，具体集合以 `apps/server/init-sql/init.sql` 的 `menu` 表为准。
> **角色菜单分配约定（init.sql `role_menu` 种子数据）**：
>
> - **管理员（role 1）**：拥有 `menu` 表全部目录/菜单级 `code`（含权限管理、商品管理全部子项），前端可见「权限管理 + 商品管理 + 大屏」。
> - **普通用户（role 2）**：菜单**收敛为「商品管理域」**——仅 `Product / Category / Attr / Trademark / Spu / Sku` 及其子项；不关联权限管理（无 `User / Role / Permission`），故前端看不到「权限管理」整块。此约束是后端种子数据决定的，与前端 `filterAsyncRoute` 自然配合。
> - **游客（role 3）**：仅商品管理域下零星几项，前端可见菜单最少。
> - **大屏（screen）**：属于 `constantRoutes`（常量路由），**不走权限过滤**，所有登录用户均可见，不依赖 `role_menu`。
> `filterAsyncRoute` 只保留前端 `asyncRoutes` 里 `name`（已 `toLowerCase()`）能对上的 `code`，多出来的会被忽略、不影响运行。所以**前端 `asyncRoutes` 子路由的 `name` 必须与 `menu.code` 对应**（菜单管理的 `code` 是 `Permission`，不是 `Menu`）；父路由无需写进 `routes`，靠子项存活。
>
> **要点**
>
> - token 同时存 pinia（运行时用）和 `localStorage`（key 为 `token`，刷新后恢复），否则刷新会被守卫当成未登录踢回登录页。
> - `menuRoutes` 存的是后端返回的原始 `routes`（menu.code 数组），真正的「过滤 + 动态 addRoute」在路由守卫里完成（见步骤 4）；`name/avatar/buttons` 供页面展示与按钮级权限判断。`isRoutesAdded` 标记动态路由是否已挂载，由守卫在挂载后置 `true`、登录/退出时置 `false`。
> - 业务报错（code≠200）由 `client.ts` 拦截器统一 `ElMessage` 提示并 **throw**，store 用 `try/catch` 捕获后 `Promise.reject` 对外抛出，业务层（登录页）再 `catch` 提示，不重复弹窗。
> - `client` 当前没注入 token 头，需在步骤 5 补上，否则登录后 info 会被后端 401 拒绝。

## 步骤 4：给 `src/router/index.ts` 加守卫

> **`router.beforeEach` 是什么？**
> 它是 vue-router 的**全局前置守卫**：每次路由「即将跳转、但还没真正跳」时先调用，可拦截导航、决定放行/改道。参数：`to`（目标）、`from`（来源）。`async` 是因为里面要 `await getUserInfo()`。
>
> **用 `return` 返回值控制导航**：`return true` 放行、`return { path }` 改道、`return { ...to, replace: true }` 用新路由表重匹配。
>
> **为什么用 `return { ...to, replace: true }` 而非直接放行？** `getUserInfo` 里刚 `addRoute` 挂上动态路由，直接放行用的是挂载前的路由表，目标页还不存在 → 白屏/404；`replace: true` 会中断当前导航、用新路由表重新匹配一次，动态路由已存在才能正确进入。

```ts
import { createRouter, createWebHashHistory } from 'vue-router'
import type { RouteRecordRaw } from 'vue-router'
import { constantRoutes, asyncRoutes, anyRoute } from './routes'
import { useUserStore } from '@/store/modules/user'
import { filterAsyncRoute } from '@/utils/routeFilter'

const router = createRouter({
  // 哈希模式（部署简单，不需要服务器配置）
  history: createWebHashHistory(),
  routes: constantRoutes,
})

// 白名单：免登录也能访问的页面
const whiteList = ['/login', '/404']

// 路由前置守卫（全局）：负责鉴权 + 动态挂载权限路由
router.beforeEach(async (to, _from, next) => {
  const userStore = useUserStore() // pinia 已在 main.ts 中注册（顺序在 router 之前），可直接使用
  const token = userStore.token

  // ① 已登录：放行
  if (token) {
    // 目标本身就是白名单（登录页 / 404），直接放行，不触发任何用户信息请求。
    // 避免「localStorage 残留旧 token + 后端 500 → 跳首页失败 → 跳回登录页」的循环。
    if (whiteList.includes(to.path)) {
      next()
    } else {
      try {
        // 同一个 session 内只拉一次用户信息并挂载一次动态路由
        if (!userStore.isRoutesAdded) {
          // 拉用户信息（含 routes/buttons/name/avatar）
          await userStore.getUserInfo()

          // 按后端 routes 过滤异步路由
          const userAsyncRoute = filterAsyncRoute(asyncRoutes, userStore.menuRoutes as string[])

          // 逐个 addRoute（动态挂载）
          userAsyncRoute.forEach((route: RouteRecordRaw) => {
            router.addRoute(route)
          })
          // 最后挂 anyRoute 做 404 兜底（必须在动态路由之后）
          router.addRoute(anyRoute)

          userStore.isRoutesAdded = true

          // 重新进入目标路由（确保 addRoute 生效后再放行）
          next({ ...to, replace: true })
        } else {
          next()
        }
      } catch (error) {
        // 获取用户信息失败（token 失效等）→ 清登录态跳登录
        userStore.clearAuth()
        next({ path: '/login' })
      }
    }
  }
  // ② 未登录：白名单放行，否则去登录页
  else {
    if (whiteList.includes(to.path)) {
      next()
    } else {
      next({ path: '/login' })
    }
  }
})

export default router
```

## 步骤 5：注入 token（只用 openapi 客户端 `client.ts`）

> **本仓库只走 `client`（`openapi-fetch`），不再使用 axios（`utils/request.ts` 已废弃删除）**，所以只需在 `client.ts` 一处注入 token 即可，无需再维护 axios 拦截器。

后端 JWT 中间件（`pkg/middlewares/auth.go`）只读标准 `Authorization` 头、按 `Authorization: Bearer <token>` 解析，**不认自定义的 `token` 头**。前端从 `localStorage` 的 `token` 字段读取并注入。

`client.ts` 用官方推荐的 **Middleware（`client.use`）** 做三件事：① 注入 `Authorization` 头（否则登录后的 info 等接口会被后端 401 拒绝）；② 处理非 2xx 的 HTTP 错误；③ 处理 HTTP 2xx 但业务 `code ≠ 200` 的情况。

> **方案 B 的关键约定：失败即 throw，业务层用 `try/catch`**
> 第 ③ 件里业务码非 200 时，中间件会 `throw`（而非仅提示）。这样无论失败来自网络、HTTP 还是业务码，`await client.*` 都会抛异常，store 用 `try/catch` 统一兜住（见步骤 3），不会出现"HTTP 200 但业务失败被当成成功"的漏判。全局已 `ElMessage` 提示，业务层无需重复弹窗。（注：日常业务拦截用 Middleware 即可，自定义 `fetch` 留给替换底层请求引擎的特殊场景。）

```ts
import { ElMessage } from 'element-plus'
import createClient from 'openapi-fetch'
import type { paths } from './schema'
import 'element-plus/es/components/message/style/css'

// 走 vite 的 /api 代理（见 vite.config 的 server.proxy）
// baseUrl 留空：请求路径写完整后端路径 /api/v1/...，由 vite 代理原样转发，
// 同时和 schema.d.ts 里的 paths 键（/api/v1/...）完全一致，类型才能匹配。
export const client = createClient<paths>({
  baseUrl: '',
})

// 统一的请求/响应拦截（中间件）
client.use({
  // ① 请求前注入 token（Bearer）
  onRequest({ request }) {
    const token = localStorage.getItem('token')
    if (token) {
      request.headers.set('Authorization', `Bearer ${token}`)
    }
  },

  // ② 响应拦截：区分 HTTP 错误与业务码错误
  //    （openapi-fetch 的 Middleware 没有 onResponseError，统一在 onResponse 里处理）
  onResponse: async ({ response }) => {
    // HTTP 层错误（4xx/5xx）
    if (!response.ok) {
      if (response.status === 401) {
        ElMessage({ type: 'warning', message: '登录已过期，请重新登录' })
      } else {
        ElMessage({ type: 'error', message: `请求失败（${response.status}）` })
      }
      // 抛错以便调用方在 catch 中感知（否则 HTTP 失败会被当成成功）
      throw new Error(`请求失败（${response.status}）`)
    }

    // 业务码错误（HTTP 200 但 body.code !== 200）
    const contentType = response.headers.get('content-type') ?? ''
    if (!contentType.includes('application/json')) return

    const data = (await response.clone().json()) as { code?: number; message?: string }
    if (typeof data.code === 'number' && data.code !== 200) {
      ElMessage({ type: 'error', message: data.message ?? '请求失败' })
      // 抛错以便调用方在 catch 中感知（openapi-fetch 默认不会因业务 code 失败）
      throw new Error(data.message ?? '请求失败')
    }
  },
})
```

## 补充：左侧菜单如何拿到动态路由

> 动态路由通过 `router.addRoute` 挂上后，**菜单组件并不会自动感知**——`Menu` 拿的是传入的 `:menu-list` 数组。所以布局页需要把「常量路由 + 按当前用户过滤后的异步路由」组合后传给 `Menu`，菜单才显示得出来。

`src/layout/index.vue` 里：

```vue
<script setup lang="ts">
import { computed } from 'vue'
import type { RouteRecordRaw } from 'vue-router'
import { asyncRoutes, constantRoutes } from '@/router/routes'
import { useUserStore } from '@/store/modules/user'
import { filterAsyncRoute } from '@/utils/routeFilter'

const userStore = useUserStore()

// 菜单 = 常量路由（所有人可见）+ 按当前用户权限过滤后的异步路由
const menuList = computed<RouteRecordRaw[]>(() => [
  ...constantRoutes,
  ...filterAsyncRoute(asyncRoutes, userStore.menuRoutes as string[]),
])
</script>

<template>
  <div class="layout_slider">
    <Logo />
    <Menu :menu-list="menuList" />
  </div>
</template>
```

> ⚠️ 若这里只传 `constantRoutes`，登录后菜单就只剩首页、大屏等常量项，后端返回的权限路由不会显示（这是动态路由已 `addRoute` 但菜单数组没接上的典型现象）。

## 常见坑（执行时遇到对照）

- **动态页面白屏 / 404**：忘了 `return { ...to, replace: true }`，或 `anyRoute` 没在最后 `addRoute`。
- **菜单显示不对**：后端返回的 `routes` 与前端 `asyncRoutes` 子路由 `name` 对不上（大小写已被 `toLowerCase()` 兜住，所以多是 `name` 本身就写错，如写了前端不存在的 `Home`，或后端 `code` 与前端 `name` 完全不同）。父路由无需写进 `routes`，靠子项存活。
- **`ElMessage` 报未定义**：本项目用 `unplugin` 自动导入，直接在 `<script setup>` 里用即可，不要手动 `import`。
- **首次打开登录页偶发 500 请求 / 登录页进不去**：`user.ts` 中 `token` 从 `localStorage` 读取，刷新页面时可能携带**上次残留的 token**。原守卫在 `token` 存在时无条件拉 `/api/v1/acl/user/info`，若后端因 token 失效返回 500，会陷入「跳首页失败 → 跳回登录页」循环并在控制台报错。修复方式见步骤 4 守卫代码：在「已登录」分支**前置白名单短路**——目标为 `/login` 或 `/404` 时直接 `next()`，不触发任何用户信息请求。这样用户主动访问登录页（或刷新后想回登录页）不会再因残留 token 引发异常。
