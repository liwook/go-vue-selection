# 13. 阶段 16：打包与上线部署 实现指南

> 本项目是**哈希路由 + 纯静态产物**，部署形态极简：把 `pnpm build:prod` 产出的 `dist/` 丢到任意静态服务器即可，无需服务端配 rewrite 兜底。前端通过 `openapi-fetch` 调用后端，**`baseUrl` 留空、请求路径写完整的 `/api/v1/...`**（见 `src/api/client.ts`），因此前端**不读取任何 API 地址环境变量**——生产跨域完全靠同源 Nginx 反向代理 `/api` 解决，无需在前端写死后端地址。

> 文档在「传统部署」基础上，额外提供 **Docker 镜像化（dist + nginx 同镜像）** 的进阶做法。

## 0. 为什么部署这么简单 {#s0}

- 路由用 `createWebHashHistory`（哈希模式）→ URL 里的路由在 `#` 后，刷新不会打到服务端路径，无需 `try_files` 兜底。
- **前端不读取任何 API 地址环境变量**：`src/api/client.ts` 的 `baseUrl: ''`，请求路径直接写完整 `/api/v1/...`；生产跨域靠同源 Nginx 反向代理 `/api` 解决（见第 2 节），因此**无需创建 `.env.production`、也无需在前端配置后端地址**。
- `build` / `build:prod` / `build:test` 脚本已在 `apps/web/package.json` 就位（`build:prod` = `vue-tsc -b && vite build --mode production`）；仓库根目录另提供 `pnpm build` 一键构建入口。

---

## 1. 上线最小三步（写死后端地址版） {#s1}

1. 跑 `pnpm build:prod`（或根目录 `pnpm build`）生成 `dist/`。**无需创建任何 `.env` 文件**——前端 `baseUrl` 留空，后端地址由部署侧 Nginx 反代决定（见第 2 节）。
2. 把 `dist/` 上传到静态服务器（nginx / Vercel / 对象存储+CDN / GitHub Pages 均可）。
3. 若用同源 Nginx 反代（推荐），按第 2 节配置 `location ^~ /api/` 转发到后端，否则浏览器直连后端会跨域。

## 2. ✅ 推荐做法：同一个 Nginx 托管前端 + 反代后端（同源部署） {#s2}

### 2.1 为什么推荐同源部署 {#s2-1}

比起把后端 IP 写死进前端 JS，更推荐用**同一个 Nginx 实例同时托管静态前端和反向代理后端接口**。好处：

- **前端不写死 IP/端口**：前端 `baseUrl` 留空、请求路径写完整 `/api/v1/...`，构建产物与后端部署位置完全解耦（**无需任何 `.env` 配置**）。
- **跨域消失**：浏览器看到的是「同源」（同一域名:80/443），请求打到 `/api`，由 Nginx 在服务端转发，根本不存在浏览器跨域。
- **换后端不重打包**：后端迁移/换 IP，只改 Nginx `proxy_pass`，`dist/` 原封不动。
- **更安全**：真实后端地址不暴露给客户端。

这是业界标准做法，尤其适合本项目（后端在 `http://127.0.0.1:9000`，接口前缀 `/api`）。

### 2.2 配套改动：前端无需配置 {#s2-2}

本项目前端**不读取任何 API 地址环境变量**（`src/api/client.ts` 的 `baseUrl: ''`，请求路径直接写完整 `/api/v1/...`），因此同源部署**不需要创建 `.env.production`、也不需要改任何前端配置**——后端地址完全由部署侧 Nginx 反代决定。直接 `pnpm build:prod` 出 `dist/` 即可。

> 若你未来想让前端可切换后端域名（例如多环境共用同一份 `dist/`），再引入 `VITE_API_BASE_URL` 并在 `client.ts` 读取；当前阶段不需要。

### 2.3 `nginx.conf` 同源部署示例 {#s2-3}

同时托管前端 + 反代后端，部署在根目录，**推荐**：

```nginx
server {
  listen 80;
  # server_name：Nginx 用来匹配"这个 server 块响应哪个域名请求"
  # 没有域名（直接 IP / localhost / Docker 内部访问）时，写下划线 _ 作通配兜底
  # 有真实域名时改成 server_name www.your-domain.com;
  server_name _;

  root /usr/share/nginx/html;   # 放 dist/ 内容
  index index.html;

  # ===== Gzip 压缩（影响最大：echarts 等 chunk 可压到 20%-30%）=====
  gzip on;
  gzip_vary on;
  gzip_proxied any;
  gzip_comp_level 6;
  gzip_min_length 256;
  gzip_types
    text/plain
    text/css
    text/xml
    text/javascript
    application/javascript
    application/json
    application/xml
    application/x-javascript
    image/svg+xml;

  # 1) 静态前端：哈希路由无需 try_files 兜底，但仍建议未命中时返回 index.html
  location / {
    try_files $uri $uri/ /index.html;
  }

  # 2) 带 hash 的静态资源（JS/CSS/图片/字体）：内容不变，长期缓存
  location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?|eot|ttf|map)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
    # JS/CSS 是纯文本，传输时由外层 gzip on 实时压缩
    # 图片（png/jpg 等）gzip 基本压不动，模块会自动跳过，无需手动关
    # 注意：location 内的 gzip 指令会覆盖外层 server 块，故此处不写 gzip off
  }

  # 3) 反向代理后端接口（可选）：浏览器请求 /api/* → 由 Nginx 转发到真实后端
  #    本仓库后端接口前缀即 /api（如 /api/v1/acl/...），proxy_pass 末尾【不带 /】，
  #    Nginx 把 /api/... 原样转发到 http://<后端地址>/api/...（保留前缀，避免 404）。
  #    若不用反代、后端地址写死进前端 JS，删掉这段 location /api/ 即可。
  #    必须用 ^~ 前缀匹配：Nginx 匹配优先级为 = > ^~ > 正则(~ / ~*) > 普通前缀，
  #    普通前缀 /api/ 会被上面的正则静态资源段(~* \.(jpg)$ 等)截胡，
  #    导致带 /api/ 的图片类请求被当成静态文件去找 /usr/share/nginx/html/... 而 404。
  #    ^~ 命中后禁止再检查正则 location，保证 /api/ 开头的请求一律走代理。
  location ^~ /api/ {
    # 单机非容器部署：填后端真实地址（端口以你后端实际监听为准，本项目后端示例为 9000）
    #   proxy_pass http://127.0.0.1:9000;
    # 同一 docker-compose 内部署：必须改用服务名，见 2.4（容器内 127.0.0.1 指向自己，写 127.0.0.1 会连不到后端）
    # 注意：proxy_pass 末尾【不要】带 /，否则 Nginx 会剥离 /api 前缀，把 /api/v1/... 转成 /v1/... 导致后端 404。
    proxy_pass http://backend:9000;   # backend = compose 里 backend 服务名；9000 = 后端容器内端口（末尾不带 /）

    # 基本头：透传客户端真实信息
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # ===== 生产级加分项 =====

    # 1) 关闭缓冲：对实时 / 流式(SSE) 接口很重要，避免响应被攒批
    proxy_buffering off;

    # 2) 启用 HTTP/1.1 长连接：减少握手开销
    proxy_http_version 1.1;
    proxy_set_header Connection "";

    # 3) WebSocket 支持（以后用到时取消注释；注意启用时上面的 Connection "" 要改为 upgrade）
    # proxy_set_header Upgrade $http_upgrade;
    # proxy_set_header Connection "upgrade";

    # 4) 超时分级：连接慢快速失败，读写给足时间
    proxy_connect_timeout 5s;
    proxy_send_timeout 30s;
    proxy_read_timeout 60s;

    # 5) 禁止重定向改写：避免后端返回 302 时把内网 IP 泄露给浏览器
    proxy_redirect off;
  }
}
```

- 后端接口带 `/api` 前缀（如 `/api/v1/acl/...`），故 `proxy_pass http://backend:9000` 末尾**不要**加 `/`（否则前缀被剥离导致 404）；单机非容器场景改为 `http://127.0.0.1:9000`。
- 上线步骤：`pnpm build:prod` 出 `dist/` → 放进 `root` → 启用 `location ^~ /api/` 反代 → 重载 Nginx（**无需**任何 `.env` 文件）。

### 2.4 实操示例：用 docker-compose 拉起 Nginx 并挂载配置与 dist {#s2-4}

上面说的"同源部署"用 **`deploy/docker-compose.yaml`** 表述最清晰，前后端一起编排、一条命令拉起，**不需要把前端打进镜像**——用官方 `nginx` 镜像挂载本地 `dist/` 和配置即可。

> ⚠️ **以下 `deploy/` 目录与文件当前尚未在仓库中创建**，属规划示例，实际落地时按此结构新建：
>
> ```tree
> deploy/
> ├── docker-compose.yaml          ← 编排文件
> └── nginx-conf/
>     └── vue-admin.conf           ← 同源配置（见 2.3 节，已带生产级加分项）
> ```

#### docker-compose.yaml

```yaml
# docker-compose.yaml
services:
  # 前端：Nginx 托管 dist + 反代后端
  web:
    image: nginx:1.30.4-alpine # 精确补丁版本（1.30.4 stable，2026-07-15 发布），生产环境可重现、避免意外漂移
    container_name: vue_admin_web
    ports:
      - '8080:80' # 浏览器访问 http://localhost:8080（这是前端 Nginx 容器对外端口，与后端 9000 无关）
    volumes:
      # 注意：compose 内相对路径是相对于本 compose 文件所在目录（deploy/）解析，
      # 而非执行命令的目录，所以 ../dist 指向仓库根的 dist/，./nginx-conf 指向 deploy/nginx-conf/
      - ../dist:/usr/share/nginx/html:ro # 前端产物（只读，需先 pnpm build:prod）
      - ./nginx-conf:/etc/nginx/conf.d:ro # 整目录挂载，直接覆盖镜像默认 conf.d（只读）
    depends_on:
      - backend # 确保后端先起（仅顺序，不保证就绪）
    networks:
      - app-net

  # 后端示例（按你自己的镜像替换 image / ports / environment）
  backend:
    image: your-backend-image:latest # ← 换成真实后端镜像
    container_name: vue_admin_backend
    expose:
      - '9000' # 后端容器内监听端口（须与后端程序实际监听端口一致），仅容器内可达
    networks:
      - app-net

networks:
  app-net:
    driver: bridge
```

#### 启动

```bash
# 1) 先构建前端产物（在仓库根目录执行）
pnpm build:prod   # 产出 dist/

# 2) 启动（在仓库根目录执行，用 -f 指定 compose 文件）
docker compose -f deploy/docker-compose.yaml up -d
# 启动后浏览器打开 http://localhost:8080 即可看到前端页面（端口见 compose 中 web 的 ports 映射）
```

#### ⚠️ 容器内 `127.0.0.1` 指向容器自己

上面 `nginx.conf` 里若误写为 `proxy_pass http://127.0.0.1:8080/`，**在容器里这个地址指向 Nginx 容器自身**，而不是后端（且端口 8080 是前端对外端口、后端实为 9000）。在 compose 网络里正确写法：

1. **后端是同一 compose 里的服务**（推荐，如上配置）：用**服务名**解析

   ```nginx
   proxy_pass http://backend:9000;   # backend = compose 里 backend 服务名；9000 = 后端容器内端口；【末尾不带 /】，保留 /api 前缀
   ```

2. **后端跑在宿主机上**（非容器）：直接用宿主机**内网 IP** 最简单，跨平台一致，无需额外配置

   ```nginx
   proxy_pass http://192.168.1.50:9000;   # 换成你宿主机的真实内网 IP + 后端端口；【末尾不带 /】
   # 前提：后端监听 0.0.0.0（非 127.0.0.1），且防火墙放通该端口；IP 变化时需同步改这里
   # （不推荐 host.docker.internal：Mac/Win 可用但 Linux 需额外 extra_hosts 配置，跨平台麻烦）
   ```

3. **后端和 Nginx 真在同一容器**（不推荐，仅演示，与上述 compose 双容器方案不同）：才用 `127.0.0.1:9000`。

#### 改配置后如何生效

```bash
# 改了 deploy/nginx-conf/vue-admin.conf 后，重载配置（无需重建容器）
docker compose -f deploy/docker-compose.yaml exec web nginx -s reload

# 想连镜像一起重拉（如升级 nginx 大版本）
docker compose -f deploy/docker-compose.yaml up -d --pull always
```

### 2.5 子路径部署注意项 {#s2-5}

部署在子路径（如 `example.com/admin/`）时：在 `vite.config.ts` 设 `base: '/admin/'`，并把前端 `location` 改为 `location /admin/ { ... }` 即可。**后端反代段不变**：仍用 `location ^~ /api/ { proxy_pass http://backend:9000; }`（注意这里 `/admin/` 是站点子路径、`/api/` 是后端前缀，二者无关）。

### 2.6 一个坑：`vue-tsc` 类型检查 {#s2-6}

- ⚠️ **`vue-tsc -b` 类型检查会卡人**：`build:prod` 脚本是 `vue-tsc -b && vite build`，先全量类型检查再打包。注意 **`dev` 模式（`vite`）只用 esbuild 转译、不做类型检查**，所以"dev 能跑"不代表类型干净——`build:prod` 才首次真正查类型，可能冒出 dev 时从未见过的类型错误（用 `pnpm build:prod` 看报错逐一修，或临时改成只 `vite build` 跳过检查）。根目录的 `pnpm build`（= `pnpm --filter web build`）也会触发同样检查。子路径部署的 `base` 配置坑见 2.5 节。

## 3. 🐳 进阶：Docker 镜像化（dist + nginx 同镜像） {#s3}

> 把 `dist/` 和 nginx 打进**同一个镜像**，用容器承载整套前端 + 反代。这是比「传统传文件到服务器」更偏运维/CI-CD 的生产化做法，优势：环境一致、可版本化、易回滚、方便接入 K8s / 容器编排。

### 3.1 思路与产物文件清单 {#s3-1}

- 用 `nginx` 官方镜像作运行基底。
- 多阶段构建：第一阶段用 `node` 镜像跑 `pnpm --filter web build:prod` 产出 `dist/`；第二阶段把 `dist/` COPY 进 nginx 的 `/usr/share/nginx/html`。
- **nginx 反代配置不进镜像**：同源反代配置（`deploy/nginx-conf/`）通过 `docker run -v` 或 compose 挂载注入，后端地址变更无需 rebuild 镜像。

> ⚠️ 同 2.4 节：**`Dockerfile` / `.dockerignore` / `deploy/nginx-conf/` 当前仓库均未创建**，下表为规划文件清单。

| 文件                 | 操作 | 说明                                                                                                                |
| -------------------- | ---- | ------------------------------------------------------------------------------------------------------------------- |
| `Dockerfile`         | 新增 | 仓库根：多阶段构建 node 构建 → nginx 托管（构建上下文即根目录，适配 pnpm workspace）                                |
| `.dockerignore`      | 新增 | 仓库根：排除 `node_modules`/`dist`/`.git`/`docs`/`*.md`/`deploy`/编辑器目录等，避免无关文件进构建上下文             |
| `deploy/nginx-conf/` | 新增 | 同源部署配置目录（含 `vue-admin.conf`），运行时通过 compose 挂载或 `docker run -v` 注入（不进镜像）                 |

### 3.2 `Dockerfile`（多阶段构建） {#s3-2}

```dockerfile
# syntax=docker/dockerfile:1.4
# 启用 BuildKit 1.4 前端解析器，支持 RUN --mount=type=cache 等语法（必须放在第一行）
# ---- 构建参数（构建时可在外部覆盖版本）----
# 版本对照：根 package.json 的 packageManager=pnpm@11.20.0、engines.node>=20
# node 用 24（LTS "Krypton"，2025-10 进入 LTS，支持到 2028，满足 >=20 且更新）；nginx 用 1.30.4 稳定线
ARG NODE_VERSION=24
ARG NGINX_VERSION=1.30.4

# ---- 阶段 1：构建 ----
FROM node:${NODE_VERSION}-alpine AS builder

# 启用 pnpm（版本由根 package.json 的 packageManager 字段锁定为 pnpm@11.20.0）
RUN corepack enable && corepack prepare pnpm@11.20.0 --activate

# 依赖下载走国内镜像（按需，内网/国内构建加速用）
RUN pnpm config set registry https://registry.npmmirror.com

WORKDIR /app

# 依赖层：只拷依赖清单（变化极少，会被缓存）
# 注意：pnpm-workspace 根目录结构，需同时拷根 package.json / pnpm-lock.yaml / pnpm-workspace.yaml
COPY package.json pnpm-lock.yaml pnpm-workspace.yaml ./
# web 子包清单（构建上下文设为仓库根时路径为 apps/web）
COPY apps/web/package.json ./apps/web/package.json

# 安装依赖（命中缓存则跳过，避免每次改源码都重装）
# 本仓库用 lefthook 做 Git 钩子（非 husky），且容器构建无 .git，钩子不会触发，无需 HUSKY=0。
# --ignore-scripts：跳过依赖的 postinstall 脚本。pnpm 11 默认拦截被忽略的构建脚本并退出码 1，
#   本项目仅 @parcel/watcher、msw 两个 dev 工具受影响（原生二进制经 optionalDependencies 分发，无需 postinstall），
#   生产构建不依赖它们，故直接跳过可避免构建失败。
# --mount=type=cache：BuildKit 缓存挂载，依赖落盘到宿主机持久区而非镜像层，
#   vue_admin_pnpm-store 缓存 pnpm 内容寻址存储（包本体，跨构建复用），
#   vue_admin_pnpm-build 缓存 pnpm 构建/索引状态，后续构建跳过网络下载显著加速。
# id 注意：id 是 BuildKit 在宿主机上的缓存命名空间，按 id 共享/隔离（同 id 共享、异 id 隔离）。
#   必须用项目前缀 vue_admin_ 区分，不同项目（如 vue_blog）要用各自前缀，禁止复用本项目的两个 id，
#   否则 pnpm-build 的索引状态会跨项目互相覆盖、命中错乱。id 仅在同一台构建机内有效，CI 干净机器无缓存可复用。
RUN --mount=type=cache,id=vue_admin_pnpm-store,target=/root/.pnpm-store \
    --mount=type=cache,id=vue_admin_pnpm-build,target=/root/.cache/pnpm \
    pnpm install \
        --frozen-lockfile \
        --ignore-scripts

# 源码层：经常变化，但不影响上面的依赖缓存
# 注意：用 pnpm workspace，需拷根 + apps/web 源码；或构建上下文设为 apps/web 并相应调整 COPY 路径
COPY . .

# 构建（生产模式）：在 web 子包下执行 build:prod
RUN pnpm --filter web build:prod

# ---- 阶段 2：运行 ----
FROM nginx:${NGINX_VERSION}-alpine

# 复制构建产物（pnpm workspace 下 web 产物的实际路径为 apps/web/dist）
COPY --from=builder /app/apps/web/dist /usr/share/nginx/html

# 注意：nginx 反代配置(含后端地址)不进镜像，由部署时挂载/环境变量注入，
# 后端 IP/端口变更无需 rebuild 镜像。详见 deploy/docker-compose.yaml。

EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

### 3.3 构建与本地运行 {#s3-3}

```bash
# 1) 构建镜像（在仓库根目录执行，Dockerfile/.dockerignore 即在根目录）
#    Dockerfile 内部会执行 pnpm --filter web build:prod 并把 apps/web/dist 打进镜像，无需本地先构建
docker build -t vue-admin:latest .

# 2) 运行容器（前端映射宿主机 80）
#    注意：nginx 反代配置不进镜像，需挂载 deploy/nginx-conf 到 /etc/nginx/conf.d，
#    这样后端 IP/端口变了只改本地文件 + 重启容器即可，无需 rebuild 镜像。
docker run -d --name vue-admin -p 80:80 \
  -v "$(pwd)/deploy/nginx-conf:/etc/nginx/conf.d:ro" \
  vue-admin:latest
```
