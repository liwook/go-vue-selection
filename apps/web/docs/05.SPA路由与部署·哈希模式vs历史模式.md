# 05. SPA 路由与部署：哈希模式 vs 历史模式

> 本文档把「SPA 路由是什么」「两种模式是怎么来的（来龙去脉）」「哈希模式和历史模式到底差在哪」「nginx 怎么部署」「刷新/直链时服务端如何找页面」「文件怎么下载」「SEO 与 SSR 是什么关系」串成一条线讲清楚。
> 以本项目的实际情况（Vue 3 + Vite + vue-router `createWebHashHistory` + 默认 `base: '/'` + 产物 `dist/`）为例。

---

## 一、什么是 SPA

**SPA = Single Page Application（单页应用）**。

核心特征：**整个网站只有一个真正的 HTML 文档（`index.html`），它就是个"空壳"**。里面没有业务数据，只有 `<script>`（打包后的 JS）和 `<link>`（CSS）。

- 业务数据 **不在** `index.html` 里，而是运行时由前端 JS 通过调用后端 API 动态获取。
- 用户"跳转到新页面"，**不是**去服务端要一个新的 `.html` 文件，而是前端 JS 根据当前 URL 决定"显示哪个组件"，把旧组件换下来、新组件挂上去。
- `index.html` 第一次被浏览器拿到后，后续"换页"只是 JS 在内存里操作 DOM，不再向服务端请求页面本身。

所以「SPA 路由」指的是：**前端 JS 自己维护一套"URL → 组件"的映射表，根据 URL 决定渲染哪个组件**，而不是交给服务端按路径返回不同 HTML。

### 一个网站真的只有一个 HTML 吗

是的——至少"应用页面的壳"只有一份 `index.html`。

但页面里引用的 **静态资源**（JS、CSS、图片、字体、`.svg` 等）是各自独立的真实文件，它们有各自的真实路径（如 `/assets/index.abc123.js`）。这些资源跟"路由"无关，浏览器按 `<script src>` / `<link href>` 里的真实路径去下载。

一句话区分：

| 类别         | 举例                    | 是否唯一 | 路径性质               |
| ------------ | ----------------------- | -------- | ---------------------- |
| 应用"页面"壳 | `index.html`            | 唯一一份 | 由路由决定显示哪个组件 |
| 静态资源     | `*.js` / `*.css` / 图片 | 多个     | 真实文件路径，下载即用 |

### 跳转新页面是否经过服务端

**应用内跳转（点菜单、按钮、`<router-link>`、编程式 `router.push`）两种模式下都不经过服务端**。这是 SPA 的本质：URL 变了，但浏览器没有真的去服务端取一个新 HTML，而是 JS 接手切换组件。

真正会"打到服务端"的，只有两种场景：

1. **首次打开网站**（浏览器去拿 `index.html`）。
2. **刷新页面 / 直接在地址栏输入或回车一个 URL / 分享链接被打开**（浏览器重新向服务端发请求）。

而这两种模式下，刷新/直链时的行为差别，正是哈希与历史模式的分水岭（见第四节、第六节）。

## 二、两种模式是怎么来的（来龙去脉）

> 很多人以为哈希模式和历史模式是"一开始就并列设计出来的两个选项"。其实不是——它们是**先后出现的**，哈希模式还曾是"歪打正着的意外发明"。理解这段来龙去脉，能帮你更自然地理解后面"两种模式差在哪、为什么历史模式要配服务端"。

### 2.1 最早：根本没有"模式"这回事（多页应用时代）

最早期的网站是**多页应用（MPA）**，规矩很简单：

> 一个网址 = 服务器上的一个真实文件。

点 `a.html` → 浏览器去服务器把整个 `a.html` 下载下来 → 整页刷新。点 `b.html` 又重新来一遍。

这时候**没有前端路由**，URL 永远对应真文件，刷新永远不出错。简单，但每次跳转都要重新加载整页，慢。

### 2.2 Ajax 革命：URL 不动了，出现新麻烦

约 2005 年后，Ajax 让 JS 能偷偷去服务器拿数据、**只更新页面局部**，不用整页刷新，体验飞升。

但冒出一个尴尬问题：**URL 不动了**。比如你看文章第 5 页，URL 还是 `article.html`。把网址发给朋友，朋友打开是第 1 页——**URL 没法"记住"你看到哪**，也没法分享具体状态。

于是大家想要：_能不能让 URL 跟着页面状态变，又不用整页刷新？_

### 2.3 哈希模式：纯属"借来的"意外发现

有人盯着浏览器自带的 `#` 锚点功能（点目录跳到页面某节），发现一个特性：

> **改 `#` 后面的内容，页面不会刷新、也不会重新请求服务器。**

那把状态塞进 `#` 不就行了？比如 `article.html#page=5`。

- 改 `#` → 页面不刷新（保住 Ajax 体验）；
- 但 `#` 变了 → URL 变了 → 能收藏、能分享、刷新后 JS 读 `#` 复原状态。

**哈希模式就这么"借用锚点机制"诞生了**，它压根不是专门设计的路由方案，而是锚点功能的意外妙用。也正因为 `#` 后面的东西服务器收不到，所以它**天生不需要服务器配合，谁都能用**。

### 2.4 历史模式：HTML5 正式"转正"

用久了，大家嫌 `#` 丑（URL 里顶个 `#` 像半成品），且 `#` 本用于锚点被路由占用了。

于是 HTML5 标准（约 2014 年普及）**正式给了个"正规武器"**：`history.pushState`。它让 JS 能**光明正大地改地址栏 URL**（不要 `#`、不刷新、不发请求）。这就是历史模式。

代价也来了：因为现在是"真路径"了（如 `article/5`），刷新时浏览器会**真的去服务器要 `article/5` 这个文件**，服务器没有就 404。所以历史模式必须让服务器"兜底"——所有找不到的路径都返回 `index.html`，交给 JS 认路（即后面第五节讲的 `try_files`）。

### 2.5 小结：不是并列选项，而是先后解法

```text
MPA 时代（无模式） → Ajax 革命 → 哈希模式（意外发现） → 历史模式（官方正经方案）
```

- 先有"无模式"的整页刷新网站；
- 大家想让 URL 记录状态，意外发现 `#` 能用 → **哈希模式**（歪打正着）；
- 标准委员会觉得该有正规方案 → **历史模式**（官方手段）。

二者是为了解决**同一个问题**（让 SPA 的"假页面"也有可分享、可刷新的 URL）而**先后出现的两种方案**，不是并列设计出来的两个选项。

### 2.6 现在哈希模式还用得多吗

**还多，远没被淘汰。** 历史模式是面向公众的"门面担当"，哈希模式是"实干老黄牛"，各占一块合理性，并非谁取代谁。

至今仍常见使用哈希模式的场景：

1. **后台管理系统 / 内部平台**（最典型）：如本项目，不靠 URL 引流、不想折腾服务端兜底，哈希"零配置、丢哪都能跑"最省心。
2. **无服务端配置权限的静态托管**：GitHub Pages、对象存储（OSS/COS）、纯 CDN、甚至 `file://` 双击打开——改不了回退规则，历史模式一刷新就 404，哈希毫无压力。
3. **桌面 / 混合 App 与微前端嵌套**：Electron、Capacitor、Cordova 本无传统 Web 服务器概念；微前端子应用也常用哈希"划一块自留地"，避免和主应用路由打架。

为什么历史模式没"消灭"哈希？因为历史模式的"漂亮"是有代价的——**必须有可控的服务器去配兜底规则**；而哈希的"丑"换来了**完全不依赖服务器**。当场景是"内部系统、静态托管、没服务器话语权"时，哈希那个唯一缺点根本不重要，优点（省心）是决定性优势。

## 三、URL 里的 `#` 是什么

以本项目哈希模式为例，URL 形如：

```text
https://example.com/#/acl/user
https://example.com/#/login
```

- `#` 之前的部分（`https://example.com/`）是真正的请求路径，会发给服务端。
- `#` 之后的部分（`#/acl/user`）**永远不会发给服务端**，它只在浏览器本地生效，被前端 JS（vue-router）读取，用来决定"显示哪个组件"。

这是浏览器历史遗留的规则：`#` 叫片段标识符（fragment），用于页内锚点定位，浏览器约定不把它发送到服务端。

## 四、两种路由模式对比

### 4.1 哈希模式（Hash Mode）

- 配置：vue-router 的 `createWebHashHistory()`。本项目即此模式。
- URL 形态：`https://example.com/#/acl/user`。
- **原理**：路由信息全在 `#` 后，浏览器刷新/直链时，实际发给服务端的永远是 `/`（或部署根），服务端永远只回 `index.html`；然后前端 JS 读 `#` 后面的内容，自己决定渲染哪个组件。

```text
用户刷新 https://example.com/#/acl/user
  → 浏览器实际请求：GET /
  → 服务端返回：index.html（永远是这个）
  → 前端 JS 读 location.hash = "#/acl/user"
  → 匹配路由表 → 渲染 User 组件
```

- **优点**：刷新、直链、分享都不会 404，**服务端零配置**（不用给 nginx 加 `try_files` 兜底）。
- **缺点**：URL 带 `#`，不够"干净"；无法利用 `#` 做真实锚点（极少场景）。

### 4.2 历史模式（History Mode）

- 配置：vue-router 的 `createWebHistory()`。
- URL 形态：`https://example.com/acl/user`（没有 `#`，像传统多页站点）。
- **原理**：路由信息被写在真实路径里，会发给服务端。应用内跳转时（JS 接管）同样不走服务端；但**刷新/直链时，浏览器会把 `/acl/user` 当成真实路径发给服务端**，服务端必须"假装"这个路径也存在、并返回 `index.html`，前端 JS 才能继续认路渲染。

```text
用户刷新 https://example.com/acl/user
  → 浏览器实际请求：GET /acl/user
  → 服务端磁盘上没有 /acl/user 这个文件/目录
  → 若不做兜底 → 404（页面白屏）
  → 正确做法：服务端把"找不到的路径"都回退到 index.html
  → 前端 JS 读 location.pathname = "/acl/user"
  → 匹配路由表 → 渲染 User 组件
```

- **优点**：URL 干净（无 `#`）。
- **缺点**：服务端必须配置兜底（nginx 的 `try_files`），否则刷新即 404；多平台（nginx / Vercel / GitHub Pages / 对象存储）都要各自配"找不到就回 index.html"，否则某些路径白屏。

### 4.3 核心对比表

| 维度               | 哈希模式                              | 历史模式                                  |
| ------------------ | ------------------------------------- | ----------------------------------------- |
| URL 形态           | `example.com/#/user`                  | `example.com/user`                        |
| 路由信息位置       | `#` 之后，**不发服务端**              | 真实路径，**发服务端**                    |
| 应用内跳转         | 不经过服务端                          | 不经过服务端                              |
| 刷新 / 直链 / 分享 | 服务端只收到 `/`，永远回 `index.html` | 服务端收到真实路径，需兜底回 `index.html` |
| 服务端配置         | 零配置（可选加 `try_files`）          | **必须**配 `try_files` 或平台等价物       |
| 刷新 404 风险      | 无                                    | 配错即 404 白屏                           |
| SEO 友好度         | 同源均为单壳，不友好                  | 同源均为单壳，不友好（见第八节）          |
| 干净 URL           | 否                                    | 是                                        |
| 本项目使用         | ✅ 是                                 | ❌ 否                                     |

> **关键共识**：除了"刷新/直链时服务端要不要兜底"这一点，**哈希模式和历史模式在功能流程上几乎一致**——最终都会回到 `index.html`，然后由前端 JS 认路渲染。差别只在"回 `index.html` 的方式"：哈希靠浏览器天然不发送 `#` 后的内容（零配置），历史靠服务端显式兜底。

## 五、`try_files` 是什么（历史模式必配）

nginx 中这行是历史模式的生命线：

```nginx
location / {
  try_files $uri $uri/ /index.html;
}
```

逐词拆解：

- `try_files`：依次尝试后面的"候选"，命中第一个存在的就返回。
- `$uri`：当前请求的真实路径（如 `/acl/user`）。先看磁盘上有没有这个**文件**。
- `$uri/`：再看有没有这个**目录**。
- `/index.html`：最后一个兜底——前面都找不到时，返回 `index.html`。

举例：

| 请求                       | `$uri` 命中？     | 结果                                 |
| -------------------------- | ----------------- | ------------------------------------ |
| `GET /`                    | `index.html` 存在 | 返回 `index.html`                    |
| `GET /assets/index.abc.js` | 文件存在          | 返回该 JS（资源，不走兜底）          |
| `GET /acl/user`            | 文件、目录都无    | 兜底返回 `index.html` → 前端 JS 认路 |

> 即使使用哈希模式，本项目 nginx 示例也写了 `try_files`，作为"未命中文件回退 `index.html`"的稳妥写法；但哈希模式下不写也不会 404（请求永远只是 `/`）。

## 六、刷新 / 直链时，服务端怎么找页面

把两种模式的"刷新 `/acl/user`"完整走一遍：

1. 浏览器向服务端发 `GET /acl/user`（历史）或 `GET /`（哈希，`#` 后不发）。
2. 服务端查找 `/acl/user` 是否存在：
   - 哈希：根本没收到 `/acl/user`，只收到 `/` → 直接回 `index.html`。
   - 历史：收到 `/acl/user`，磁盘无此文件/目录 → 靠 `try_files` 兜底回 `index.html`（没配则 404）。
3. 浏览器拿到 `index.html`（空壳），执行打包 JS。
4. JS 读取路由：`location.hash`（哈希）或 `location.pathname`（历史）。
5. 匹配前端路由表（`src/router/routes.ts` 里的 `path → 组件`），渲染对应组件。
6. 组件运行时调 API 取数据，填充页面。

**本质一句话：服务端"盲返"`index.html`，前端 JS 负责认路。** 两种模式都是这套逻辑，哈希是"天生盲返"，历史是"服务端兜底盲返"。

> 本项目还有一个规划细节：在 `src/main.ts` 入口处加 `normalizePathnameToHash()`，作为哈希模式的边界补丁——防御用户手输或误分享了无 `#` 的链接（如 `/login`），自动纠正成 `/#/login`（`src` 尚未编写，属规划步骤）。若迁移历史模式，此补丁应移除。

## 七、文件下载（两种模式都一样）

常见误解："哈希模式只发 `/` 给服务端，那怎么下载文件？"

澄清：**下载文件、加载静态资源，走的都是 `#` 之前的真实路径，跟路由模式无关。**

- `#` 只管"前端显示哪个组件"，它管不到文件下载和静态资源。
- 想下载一个文件，只要 URL 的 `#` 之前是文件的真实路径即可，例如：
  - `https://example.com/files/report.xlsx` → 浏览器 `GET /files/report.xlsx` → 服务端当作真实文件返回 → 浏览器下载。
  - 资源同理：`https://example.com/assets/index.abc.js` → `GET /assets/index.abc.js` 拿到 JS。

错误写法：`https://example.com/#/assets/index.abc.js` —— 这里的 `#` 后内容被当成"路由"，浏览器实际只请求了 `/`，根本不会去拿那个 JS 文件。`#` 之前必须是 SPA 文档（`index.html`）所在的位置，不能是资源文件。

> 结论：**能否下载、能否拿到资源，取决于路径是否在 `#` 之前，而不是用哪种路由模式。** 哈希模式和历史模式在"文件下载"能力上完全等价。

## 八、SEO 与 SSR 的关系

- **SEO（搜索引擎优化）是目标**：让搜索引擎能收录、理解页面内容。
- **SSR（服务端渲染）是手段之一**：服务端直接返回"已含正文"的 HTML，爬虫拿到即可见文字。SSG 则在构建时生成多个带正文的静态 HTML，二者都不必每次请求现渲染。

纯 SPA（无论哈希还是历史）返回的只是"空壳 `index.html`"，正文靠 JS 运行时填充，对爬虫不友好，不利于 SEO。所以：

- **后台管理类（admin）项目**：不需要被收录，用 SPA（本项目哈希模式）完全没问题。
- **面向公众的官网 / 电商详情页**：若要 SEO，需要 SSR（如 Nuxt、Next.js）或 SSG，让服务端/构建时产出带正文的 HTML。

## 九、nginx 部署要点（本项目）

- `pnpm build` 产物在根目录 `dist/`（`vite.config.ts` 未设 `base`，默认 `/`；未设 `build.outDir`，默认 `dist`）。
- 把 `dist/` 内容上传到静态服务器根目录。Linux 常见位置 `/usr/share/nginx/html`；Windows nginx 默认 `C:/nginx/html`。
- 配置文件位置：Linux 通常是 `/etc/nginx/conf.d/*.conf`（被主 `nginx.conf` 的 `include` 引入）；Windows 编辑 `nginx.conf` 或同目录 `conf.d`。
- **端口冲突**：多个 `server` 块不能都监听同一个 `listen 80` + 同一 `server_name`，否则启动报错；用 `default_server` 指定默认站点或用不同端口/域名分流。

### 哈希模式 nginx 示例（本项目推荐）

```nginx
server {
  listen 80 default_server;
  server_name localhost;
  root /usr/share/nginx/html;        # 放 dist/ 内容
  index index.html index.htm;
  # 哈希路由无需兜底也不会 404；这行是兜底未命中的稳妥写法
  location / {
    try_files $uri $uri/ /index.html;
  }
  # 如需反代后端 API（本仓库后端在 :9000，接口前缀 /admin）：
  # location /admin/ { proxy_pass http://127.0.0.1:9000; }
}
```

> 也可把 `root` 写进 `location /`，功能等价；本示例放在 `server` 层更简洁。若自行加 `error_page 500/502/503/504 /50x.html`，需自备 `50x.html`（不在 `dist/` 内），否则错误页本身也会 404。

### 历史模式迁移清单（如需切换）

1. `src/router/index.ts` 改用 `createWebHistory()`。
2. nginx（及各托管平台）必须配 `try_files $uri $uri/ /index.html;`。
3. `vite.config.ts` 设正确的 `base`（部署根目录用 `/`，子路径用 `/admin/` 等）。
4. 后端 API 加统一前缀（如 `/api/`），避免被 `try_files` 兜底吞掉。
5. 移除 `src/main.ts` 的 `normalizePathnameToHash()` 补丁。
6. 各托管平台（Vercel / GitHub Pages / 对象存储）都配"找不到即回 index.html"。

## 十、选型建议

- **后台管理 / 内部系统 / 工具类**：**推荐哈希模式**。部署零配置、刷新不 404、不依赖平台兜底，且这类项目不需要 SEO、不介意 URL 带 `#`。本项目即采用此方案。
- **强诉求"干净 URL"、或对接某些 SSO / 第三方回调对 URL 格式有要求**：再考虑历史模式，并务必配好 `try_files` 与平台兜底。
- **面向公众的、需要被搜索引擎收录的站点**：SPA 单壳不利于 SEO，应改用 SSR（Nuxt/Next.js）或 SSG，而非简单切换路由模式能解决的。

---

## 十一、一句话总结

> SPA 只有一个 `index.html` 空壳，页面切换靠前端 JS 认路，应用内跳转两种模式都不走服务端。哈希模式把路由藏在 `#` 后（浏览器不发服务端，刷新零配置），历史模式把路由写进真实路径（刷新必须服务端 `try_files` 兜底）。**文件下载和静态资源永远走 `#` 前的真实路径，与模式无关。** 后台 admin 用哈希最省心；要 SEO 得上 SSR/SSG，而非换路由模式。
